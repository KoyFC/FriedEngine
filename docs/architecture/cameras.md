# Cameras

A `fried.scene.Camera` is a component on an object with a `Transform2D`, so any component can move it by moving that transform, which is what makes following another object fall out of the `update()` that already exists instead of needing a mechanism of its own: the sandbox's `CameraFollow` is a component on the camera's object, or below it, that moves the transform. Its position is the point of the world that lands at the center of the view, because that is the form a camera that follows something needs; a top left origin would make every follow write the same half-viewport subtraction. It holds a `zoom` and nothing else. Rotation and scale are ignored, since rotating the view would have to rotate the rectangle commands too and SDL2 draws those axis aligned.

The camera belongs to the `Scene`, not to the `Renderer`. That is what makes screen space fall out for free: a scene with no camera draws in screen coordinates, so a game puts its interface in a second scene, leaves its camera null, and the interface stays still while the world moves. Nothing had to be added to `SpriteRenderer`, and a game's own drawing components need no flag, which is the test that decided it. On the `Renderer` the camera would have been one view per window, and the view is per scene, since a window draws several of them.

A command records the camera it was submitted under, the way it already records its render target, and `Scene.draw()` sets both for the length of a pass. The camera hands the queue a `CameraView`, a plain object with the position and zoom that `Camera` refreshes before each draw, so the queue reads three fields and never calls into the component. The transform is applied at dispatch, in the one place every drawn thing already passes through, rather than at every call site that computes a position. A component keeps submitting world coordinates and never learns a camera exists. `worldToScreenX`, `screenToWorldX` and their `Y` twins convert through the view of the camera's scene, or of the scene that draws through it when the camera sits in none, as the editor's own does.

`Scene.camera` is a plain field that names a camera of the scene, which a scene file does with `camera`. Destroying the scene clears it. A camera that has been destroyed but is still assigned keeps drawing from its last position, so a game that destroys its camera also sets the field to null.

Two consequences are worth knowing. A scene has one camera and a camera has one scene, so a world cannot be seen through two views at once, which a split screen would want; that needs viewports, which the renderer does not have, and a scene cannot be drawn to two renderers anyway because textures belong to the renderer that created them. And a `Transform2D` position is a corner rather than a center, since nothing in the engine has a pivot, so a camera that follows an object centers the view on that object's corner unless the game offsets it by half of what it drew, which `CameraFollow`'s offset is for.
