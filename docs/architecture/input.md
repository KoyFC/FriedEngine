# Input

Input follows Unity's naming (`isKeyPressed` for held, `isKeyDown` for the frame it went down) rather than the more common convention where `IsKeyDown` means held. All three states come from comparing SDL's live state against a previous-frame snapshot the loop refreshes once per frame.

Gamepad buttons are named by position, not by label: the face buttons are `South`/`East`/`West`/`North`, so the same game code means A on an Xbox pad, cross on a PlayStation pad or a Vita, and B on a joycon. The triggers appear as both an axis and a button, because SDL reports them only as axes and a game wants them either way.

Touch is reported per device and per finger, as positions in pixels of the window it landed on, since that is what the mouse reports and what a camera converts from. A finger's id holds from the `TouchDown` that starts it to the `TouchUp` that ends it, while its index in the polled API only counts the fingers down now, so the id is what follows one finger across frames. SDL's emulation of a left click from a touch is turned off, because a game handling both would see every tap twice, and the polled `isTouchDown()` is flagged from the events rather than compared against the previous frame, so a tap that lands and lifts within one frame still counts. A finger on a screen the game has no window on is not reported at all, since there is no window to place it in.

Input is readable two ways, and on purpose. `Input.isKeyPressed()` and its siblings ask the device, which is what game logic wants: it does not care when a key went down, only whether it is down now. `Input.events` is the same frame's keyboard, mouse, gamepad and touch activity as an ordered list of `InputEvent`, which is what anything deciding *who* gets an input wants, because only a stream can be consumed. Every event carries a `handled` flag that whoever reads the list sets and whoever reads it afterward honors.

The polled API ignores `handled` entirely, because it reads the device rather than the list, so code that asks it can always bypass whatever consumed the event. That is the same duality Hazel has between its event layers and `Input::IsKeyPressed`, and it is a known trade-off rather than an oversight: making polled input obey consumption would mean routing every query through whoever consumed the event, which is a much heavier thing than most game code asking whether a key is down.

The events are pooled and refilled every frame, the way the draw queue's commands are, so a frame of input costs no allocation after the first one, and nothing may keep an event past the frame it arrived in. Three things are deliberately not in the stream. A key the desktop repeats while it is held produces one event rather than a stream of them, because a repeat rate is a text editing concern and nothing here edits text yet. A gamepad axis is only queued when its deadzoned value changes, since a stick at rest reports noise that the deadzone flattens to the same zero and would otherwise queue an event every frame. And the triggers appear only as axes, because SDL has no button event for them: the polled `L2` and `R2` are synthesized by comparing a threshold against live state, which a queue drained once a frame has nowhere to do.

Input actions sit on top of the polled API and are pure Haxe, with nothing native behind them. An `InputAction` has a type (`Button`, `Value` or `Vector2`) and a list of `InputBinding`s, and a binding is built from `InputSource`s: a key, a mouse button or wheel axis, a gamepad button or axis, or a touch device. So one action named Move can be a stick, WASD and the arrows at once, and the game asks `move.x` and `move.y` without knowing which device answered. The composites are `Axis` (two sources as the ends of one axis), `Vector` (four sources as a direction pad, a diagonal scaled back to length 1) and `Stick` (two gamepad axes as one vector), and up reads -1 on y like the screen and the sticks do.

Every enabled action is read once a frame, between the event pump and `Time.tick()`, so `isPressed`, `isDown` and `isReleased` mean the same thing for the whole of the frame and follow the keys' naming. When several bindings are live the strongest wins instead of their sum, as in Unity, so a stick and a key held together never go past 1. A gamepad axis used as a button counts as pressed from `pressThreshold` (0.5) on. An action does nothing until `enable()`, and enabling one whose input is already held does not count as a press, which is what lets an `InputActionMap` switch a menu's actions on while the key that opened it is still down. Disabling an action zeroes it without firing `onReleased`. Evaluation writes into two static floats rather than returning a vector, since the Vita and the calculator would feel an allocation per binding per frame.

Unlike the polled API, actions honor `handled`: when a layer handles a key, mouse button, gamepad button or touch press, that source reads 0 for every action until it is let go, so a click a button took does not also fire a gameplay action bound to the same click. An action with `ignoresHandled` reads it anyway. Axes are never consumed, since they have no press to handle. Keyboard and gamepad contention between a menu and the game is left to the game: it switches which `InputActionMap` is enabled, since no layer can know which of two modes a key belongs to. Rebinding at runtime, saving bindings and reading mouse position as an action are not there yet.
