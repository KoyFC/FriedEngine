# Project file and user data

A game declares itself in a `project.fried` at its own root. It is JSON because the file is written and rewritten by programs as much as by people: `haxe.Json` parses it in macro context and CMake reads it with `string(JSON ... GET ...)`, so whatever generates one can use its own serializer.

Every field is read by something. `name` and `organization` are the identity handed verbatim to `SDL_GetPrefPath()`; the engine does not sanitize them, since a silent rewrite would move a game's save directory without its author knowing. `version` and `vita.titleId` go to the Vita packaging step, which is why the version uses the `XX.XX` shape a Vita package requires, and the Switch's NACP is built from `name`, `organization` and that same `version`, which is why the Switch added no key of its own. `window.title` is the window title. Two packages take optional text of their own, and fall back to the identity above when it is absent: `3ds.description`, the SMDH's description line, which shows the version otherwise and holds 128 characters, and `nds.subtitle1` and `nds.subtitle2`, the DS banner's second and third lines, which show the organization and the version otherwise and are limited to 31 characters each. One too long is refused at configure time rather than cut where nobody sees it. Each side reads only the keys it consumes.

`platforms` says which platforms the game builds for, and like `display` it is read only by CMake: Haxe never learns the platform, since `build/cpp` is generated once for every platform. It is a list of the names `fried_add_game` gives the platform it configures for, `pc` standing for every computer, and `cmake/ProjectPlatforms.cmake` refuses to configure for one the list leaves out, naming the platforms it declares and the key to edit. It is an allow-list, and a project that declares none builds everywhere, so existing projects are unchanged. The editor player is exempt, since it is a computer build of any project, including one that declares only the DS. The list also decides what is checked on every build, so that a limit is met on the computer a game is developed on rather than on the hardware: a PNG past the 1024 pixels a side the 3DS and DS GPUs take warns when either is listed, and the audio files the fx-CG50 build leaves out are counted when it is. A project that declares none is checked for the platform it configures for. There are no tiers: nothing a project could choose changes how the engine is built, since each platform's backends and limits follow from the platform, and the game asks the engine at run time what it can draw. If a choice ever does, it should follow from this list rather than be a second setting that could contradict it.

`display` says how the game fills the screen. Its `mode` is `default`, `fit`, `integer`, `expand`, `pixel`, `height` or `stretch`, and every mode but `default` also takes the `width` and `height` the game is designed for. Its `filter`, `nearest` unless it says `linear`, is how every texture is sampled when drawn at another size, whether the display or a transform scaled it, so it applies in `default` as well: pixel art wants `nearest`, and art drawn at a higher resolution than it is shown at wants `linear`. There is one `display` for every platform, since a game picks a design size and each screen scales it its own way: a `<platform>.display` is refused at configure time. Haxe never sees it: `build/cpp` is generated once for every platform, while CMake configures one platform at a time. `cmake/ProjectDisplay.cmake` reads it there and compiles the result into `fried_engine` as `FRIED_DISPLAY_*` definitions, rejecting an unknown mode or filter, or a missing size, at configure time. Being compiled into the engine is why one build tree holds one game.

`physicsRate` is optional and is how many fixed steps a second the game runs, 60 when it is missing; a game for a console that cannot afford them may ask for 30.

`vsync` is optional and true unless it is `false`, and `fried.Bootstrap.run()` passes it to the renderer it creates. It is only a request: the consoles and the calculator always present at their own refresh, and under XWayland the renderer is created without it regardless. With it off, `targetFps` paces the loop, and `Bootstrap` starts it at `defaultTargetFramerate` from `project.fried`, an integer where `0`, which a missing key also means, is no limit. That key is read only when vsync is off and only to start the game, so a game that lets its player choose a rate sets `Application.targetFps` itself.

`native/graphics/display.cpp` turns that into a layout: the logical size the game draws in, the viewport it lands in on the real output and the scale between the two. `fit` and `integer` center the design size and leave black bars, `integer` shrinking the way `fit` does on a screen smaller than the design rather than cropping it. `expand` keeps the design's aspect for its shorter side and widens the logical size until it covers the output, so the game sees more rather than bars, `height` keeps the design's height on every screen and widens the logical size to the screen's shape, so the game sees the same height everywhere at whatever scale that takes, which is not a whole number in general. `pixel` scales by the whole number that fits the design, never below 1, and the game sees whatever fits at that scale, so a screen smaller than the design shows less of the world instead of a shrunken one, and `stretch` covers the output with the design size, distorting it. The SDL renderer applies the layout as its own viewport and scale instead of `SDL_RenderSetLogicalSize`, which can only letterbox, and does so on every clear because SDL resets the viewport whenever the window changes size. `Renderer.width` and `height` are the logical size, read once when the renderer is created and again when its window reports a resize, before the game's `onResize` runs, since a camera reads them for every object it draws. The mouse and touch positions are converted into that size, so the game never handles output pixels.

Positions stay fractional from the transform to the backend, and are rounded once there, edge by edge, to a pixel of the real output. Rounding to whole logical pixels earlier, as the scene used to, had two costs once a logical pixel could cover several real ones: a moving object stepped by that many pixels at a time, and an object and the camera following it were each rounded on their own, so it shook against the world it stood in. Rounding the edges rather than the position and the size keeps two images placed side by side touching, and rounding at all keeps the nearest filter from sampling a texture between its texels.

`fried.Project` exposes the identity as macros folded into constants, so the file is an input to the build rather than something the game ships and opens at runtime. A missing or malformed file is one fatal error, since it is one fact about the whole project; a missing field is an error per call site, so one compile reports all of them. Unknown keys are ignored, so a file declaring more than this version consumes still builds. CMake registers it in `CMAKE_CONFIGURE_DEPENDS`, so editing it cannot produce a package with stale values.

Nothing under the asset root is writable, and that is not a rule the engine chose: the Vita mounts `app0:` read-only and the Switch mounts `romfs:` read-only, so an asset API with a write side could not be implemented there anyway. Anything that has to survive a run goes through `fried.io.UserData`, whose root is resolved per platform from that identity, by SDL wherever it can answer and by the engine on the Switch, where it cannot. It throws rather than falling back to another directory if SDL cannot resolve one, because a game silently saving somewhere nobody asked for is worse than one that does not start. It reads and writes text and JSON, the latter being `haxe.Json` over the text calls; writing creates any missing directory under the root.
