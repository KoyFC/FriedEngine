# Collisions

A `fried.physics.Collider` is an axis aligned box and a component on an object with a `Transform2D`, so the thing that collides is an object of its own under the one that owns it, and an object can have several of them to cover a shape one box cannot. Its position is the box's top left corner in its parent's space, which is what an offset used to be, and it follows its parent. It holds a local `width` and `height`, and its world bounds are those multiplied by the world scale, which is what `SpriteRenderer` does with a texture's dimensions and for the same reason: a stored world size would be a second truth that a scale change could contradict. Rotation is ignored, as it is by the camera, because an SDL2 rectangle is axis aligned and a rotated box is a different test with a different cost.

The bounds are floats, so `fried.graphics.Rect` is not what a collider is made of. `Rect` is integers and names either a region of a texture or a rectangle to draw, and a collider that rounded its edges would stop a mover at a different place than it was asked to stop. `Rect` still appears in the collider, for the debug outline, which is a rectangle to draw.

A negative size is normalized rather than refused: `left` is always the smaller edge, so a sprite flipped by a negative `scaleX` collides where it is drawn instead of disappearing from every query.

Queries live in `fried.physics.Physics` and take the scene they are asking about. A query is a question about one world and the scene is what holds the objects of that world, so the scene is the argument rather than a global the engine would have to be told about. A collider is a component that asks for the collider list through its `hookFlags()`, so `Scene` knows about colliders only as a list of components it was told to keep.

The scene keeps its colliders in a list that is refilled with the other hook lists, in tree order, and in a `ColliderGrid` that is refilled with it. The list is the tree's, so it cannot disagree with the scene: a collider that leaves the scene is gone from the next list, and one whose ancestor is inactive is skipped by the `isOn` flag, the rule `update` and `draw` already follow. A query asks the grid for the colliders near the box it is about and tests those, checking `isOn` as it goes, and it is evaluated when it is asked, so it sees an object another component moved or switched off earlier in the same frame.

A collider keeps its box in world space as four integers and works them out again only after it, an ancestor or its size changed, because on the DS every operation on a `Float` is a call into software floating point and a query tests each candidate. The integers are in 20.12, a pixel being 4096 units, worked out in `native/math/fixed_point.h` from the bits of the doubles, the same conversion the DS renderer uses, so a test compares integers. A collider that is in a scene does not even go through doubles for them: the transform store that holds its transform's world position (see Game objects) works the box out from its own numbers and the collider's width and height, in the same units, so reading a box costs one native call and no conversion of a `Float`.

The answer is the same on every platform, except that on the DS a position that needs a rotation comes from a sine table in 16.16 and can differ from the other platforms by a small fraction of a pixel (0.05 at most in a hierarchy four turns deep and 450 pixels across), which can move a box across an edge it was touching. Positions are rounded down to a unit, so two boxes that are less than 1/4096 of a pixel apart or overlapping may be taken for touching, which is not an overlap, and a position past a quarter of a million pixels saturates. `left`, `right`, `top` and `bottom` give the exact `Float` box, worked out only when one of them is read, and `raycast`, which divides, uses those.

The boxes and the grid are kept natively, in a `ColliderStore` (`native/physics/collider_store.cpp`): one array of boxes, each collider at its place in tree order, so a query walks integers that are next to each other and not objects scattered through the heap, which matters on the DS with its 4 KB data cache. The Haxe `ColliderGrid` only keeps which collider is at which place and which ones moved, and tells the store each box when it changes. A query for what overlaps a box is answered whole by the store, which gives back the places in tree order, and Haxe only checks `isOn` and the collider to ignore.

The grid has 64 pixel cells hashed into 256 buckets, so the world has no edge and nothing is allocated while the game runs, and two cells that share a bucket only add a candidate that the query's own test turns away. It is not rebuilt each frame, which would be wrong for a game that moves an object and asks a question straight away: a collider that moves, is moved by an ancestor or changes size queues itself, and every query empties the queue before it looks, refiling only the colliders whose cells changed. The whole grid is refilled only when an object enters or leaves the scene. A collider that covers more than 16 cells is tested by every query, and a query that covers more than 16 tests every collider, so a long ray or a wide box is as slow as it was before the grid and no slower.

The grid keeps no order, so what a query returns is put back in tree order, which the store does for the overlap queries: a query that returns one collider returns the first in the tree that matches, `overlapBoxAll` fills its list in tree order, and of two colliders a ray enters at the same distance it reports the later one, which is what testing them in order did. A step of a `KinematicBody` asks for the colliders its box can reach in that step once, and tests its two axes and its overlaps against them.

An object that has to move and be stopped has a `KinematicBody` on its own object or on a child, next to its `Collider`, the way `CameraFollow` sits with the camera it moves. The body moves the first `Transform2D` it finds at or above its object, and its collider is the one on that transform's object or, failing that, the first on a child.

The body holds a velocity in pixels a second, and the scene moves every body once in each fixed step, after the fixed updates that set the velocities: the object moves along x and is backed out of the deepest solid collider it ran into, then the same along y, so a run into a wall slides along it and stops at contact and not short of it. A body is a component and not a base class because a game's own class that moves an object has a base of its own, and a class has one.

Which colliders stop which is decided by integers before any `Float` is compared: a collider sits on the layers of `collisionLayer` and a body is stopped by, and told about, the layers of its collider's `collisionMask`. A trigger collider stops nothing and is only reported, in the `contacts` of every body whose mask names it; a body whose own collider is a trigger is never stopped and `contacts` holds everything it overlaps, which is what a shot that must hurt what it touches and pass through the rest needs. Bodies move in tree order, so one that moved earlier in the step is an obstacle to those after it, and a body that is switched off neither moves nor blocks. The object is moved in its own coordinates, which are the world's while its parent is not scaled or turned.

A game reads `contacts`, `isBlockedX` and `isBlockedY` in its next `update` or `fixedUpdate`; they are those of the last step, and a frame that ran none leaves them as they were.

Touching edges do not overlap, so a mover resting exactly against a wall is not inside it, and `containsPoint` is inclusive on the left and top edges and exclusive on the right and bottom ones, so two boxes side by side never both claim the same point.

`Physics.raycast` is the slab test, returns the nearest hit within `maxDistance` and normalizes the direction itself, so a caller passes the direction it already has and reads a distance in world units rather than in multiples of whatever length that vector happened to have. The hit carries the normal of the face the ray entered through, which is what a slide or a bounce needs and what the entry axis already knows. A ray that starts inside a collider hits it at distance zero with a zero normal, because "is there something where I am" is the same question, and there is no face to name. A direction of zero length points nowhere, so it warns and returns nothing instead of dividing by it.

A `RaycastHit` is allocated per hit and its fields are read only, rather than one shared instance refilled per cast. A shared hit reads the same at the call site and holds different values a frame later, which is a bug that only appears once a game keeps one.

Debug drawing belongs to the collider, behind `isDebugVisible`. A collider is invisible by definition, and the usual first bug is one that does not sit where the sprite does, which is a thing to look at rather than to infer from logs. The cost is that a collision node knows about the draw queue, and it is paid only when the flag is on: the outline's `Rect` is allocated the first time one is drawn. Pressing F5 in the sandbox turns on every collider in the scene.

Nothing here moves anything. A query answers and returns, and what to do about the answer is the game's, which is why there is no solid flag, no trigger, no layer mask and no collision callback: each of those is a policy, and the engine has no way to know which one a game wants. `sandbox/src/components/Player.hx` is the policy a game writes instead, and it is short: it steps one axis at a time and, when the step ends inside something, backs out by exactly the depth it went in, so running into a post along one axis still slides along the other. It resolves against one collider per step, which is all the sandbox's spacing can produce.
