# Editor player

The editor cannot link the engine, since a project's nodes are compiled Haxe and the engine is a set of static singletons, so its viewport is a game of its own: `editor/player/`, built with `-D fried-editor` through the same `fried_add_game()` as any project. Everything it adds is under that define, so a shipped game contains none of it.

It is started as `fried_editor_player --editor-port N --width W --height H --engine-assets DIR --game-assets DIR` and connects to the editor over loopback TCP, which keeps stdout free for `Log`. A message is a 32-bit little-endian length and then JSON, and one that carries a `pixels` count is followed by that many raw bytes. The player says `hello` first, with the protocol version, which is 5. The editor can ask for `schema` (every node class with the class it extends and the fields it declares itself, with kinds and default values read from a real instance so the inspector shows what the engine does, one section per class), `load` (a whole scene, and the size of the screen to lay it out against), `setField` (one field of a node, which covers dragging; `name` is handled apart), `setEditorCamera`, `setEditorCamera3D` (the editor's own camera for a 3D scene, which the scene draws through in place of the one it names), `setEditorView` (`2d` or `3d`: a 2D view leaves out the meshes, and a 3D view leaves out the nodes that are drawn flat), `setPreview` (a preview draws the scene as the game would, through the cameras the scene file names and with both kinds of drawing, which is what the editor's Game tab shows when the game is not running; the editor sizes the window to the game's display for it) and `resize` (the window and its renderer take the size of the panel that shows them, through `Window.setSize()`, which a console ignores), then `render`, which answers with a `frame`: RGBA pixels and a box in world coordinates for every drawn node in tree order, and for a node under another drawn node the world position, rotation and scale of that parent, so the editor turns a drag in the world into the node's own coordinates. A `Node3D` is not in that list but in `bounds3D`, in the pixels of the frame: the box of its mesh, its distance, its origin and where one more unit of its x, y and z lands, since those follow its parent's axes. The frame also lists `frusta`, the eight corners in the world of what each `Camera3D` of the scene file sees, shaped by the aspect of the screen the scene is laid out for, out to its far plane. A failed request answers with an `error` and leaves the scene that was showing. The editor changes the structure of a scene in place: `addNode` (a parent, an index and the node as the file spells it, with its children), `removeNode` and `moveNode`, so a scene of thousands of nodes is not built again for each edit. What cannot be said that way, such as a node changing class, is a `load`. Nodes added or moved are not readied, as no node of the player's scene is.

A frame carries a box for every drawn node, in tree order, with the node's origin in the world as `originX` and `originY`, since a box does not always start at it (a camera is a marker centered on it, and a box with a negative scale starts at its far edge), and, for a node whose parent is drawn, the parent's world position, rotation, scale and size, so the editor can put a handle where the node is and turn a drag in the world into the node's own coordinates. A scene is drawn by `EditorSceneLayer`, which draws and never updates, so no game logic runs while editing, and layout still runs because it is part of reading a world position. The scene's view is the project's display size and not the panel's, so what is anchored to an edge does not move when the panel is resized. The view is the player's own `Camera`, swapped in for the scene's and never saved, so the editor draws selection, gizmos and the display frame itself from the boxes it is sent. Both ends of the link turn Nagle's algorithm off, since two small requests in a row would otherwise wait out a delayed acknowledgement, about 40 ms, for each frame. The player runs at 60 frames a second while idle and 240 for a moment after each request, and draws only when a frame was asked for. Frames are read back by `Renderer.readPixels()` from `Application.onBeforePresent`, which is the only change to the loop, and the whole thing renders on request. The asset roots are the project's own folders, through `Filesystem.overrideRoot()`, so an edited asset is seen without copying it beside the executable. A project whose nodes a scene file uses has a player of its own. It adds an `editor.hxml` beside its `build.hxml`, with `-D fried-editor` and a main class that registers its nodes and calls `EditorPlayer.run()`, and the editor builds it with `haxe editor.hxml` and the CMake project in `editor/project-player/`, which calls `fried_add_game()` with the project's folder from outside it. The player's entry point is `fried.editor.ProjectPlayer`, which finds the nodes the same way, so the `editor.hxml` is only a copy of `build.hxml` with that main. The player leaves the project's display out, since it draws one to one and the editor shows the display as a frame. Running it without a display takes `SDL_VIDEODRIVER=offscreen`, which the editor sets: SDL then makes an EGL context with no window behind it, the player draws meshes with it as the sandbox does, and where there is no EGL its renderer falls back to SDL's software one, which draws meshes as triangles.

A project's own player can also run the game. Started with `--mode play`, `fried.editor.ProjectPlayer` hands over to `PlayRunner`, which is a `BootObserver` that `Bootstrap` tells how the game goes, and the game itself is started by `Bootstrap` as in a shipped game, autoloads included, with the project's display size and its nodes. It says `hello`, then waits for `play`: the name and the data of the scene the editor is showing, and whether to start from it or from the project's start scene. That scene is registered in place of the file of the same name through `SceneManager.replace()`, so the game sees the changes the editor holds if it comes back to it, and `Bootstrap.startSceneOverride` opens it. The game runs for real: logic, physics, audio and every layer. `setField`, `addNode`, `removeNode` and `moveNode` are answered by `SceneEdits`, the same code the editor player uses, against the scene on screen, and a failed one answers with an `error` that does not stop the game. Every frame is sent as a `gameFrame`, with the pixels at the display's size and `stats`: frames per second, the milliseconds a frame takes, the milliseconds spent updating and drawing, the nodes in the scene and, when the player is built with `-D fried_profile` (see [Profiling](../development/profiling.md)), `sections`: the average milliseconds of each `Profile` section. The game sends at most two frames the editor has not said it drew with `frameShown`, and `showGame` with `visible: false` stops them, so a slow or hidden editor drops frames and never slows the game. The game's window is offscreen and never has the keyboard or the mouse, so the editor sends them: `key` (an SDL scancode and whether it is down), `mouseMove` and `mouseButton` (the position in the game's pixels, the button from 1) and `mouseWheel`. `Input.inject()` queues them and the next frame's events take them in, as a real event would, setting the keys, the buttons and the mouse that `isKeyDown`, `isButtonPressed`, `mouseX` and the rest answer from, and the events that buttons and controls receive. Once the editor has sent one, the window's own keyboard and mouse are no longer read. Gamepads are read through SDL as in a game, with `SDL_JOYSTICK_ALLOW_BACKGROUND_EVENTS` set so that a window without focus still reports them. `pause` with `paused: true` suspends the game through `Application.isSuspended`, which stops every update and fixed step while the frames keep coming, and silences the music until a `pause` with `paused: false` brings it back; `step` lets one frame through while it is suspended, and `speed` with a `scale` sets `Time.hostScale`, the editor's speed control, on top of the game's own `Time.timeScale`. `frameLimit` sets the game's frame rate: a number of frames a second, 0 for as many as it can draw, or a negative number for the project's own rule, which is the rate of the editor's display (sent as `refresh`) when project.fried waits for vsync or names no default frame rate, and its default frame rate otherwise. A project with no rate still gets the display's, since thousands of frames nobody sees take the graphics card the editor draws with. The game is drawn offscreen and nothing waits for a display to present it, so no compositor holds it to the display's rate. When the rate is the display's, the editor's `frameShown` takes the display's place: `Application.waitForHost` lets `PlayRunner` wait, at most 100 ms, for the editor to show the last frame instead of keeping a clock of its own, so each frame of the editor's screen gets a new frame of the game, as a built game waiting for vsync does. Any other rate is kept by the game's own clock. The editor also watches the running game's nodes. `watch` names the node being inspected and says whether every node is wanted, which is when the editor's scene view is on screen, and the game answers with `state` a few times a second: for each watched node that has an id, the fields that changed since it last said, read with `NodeType.read()`, as a list of `{id, fields}`. Pictures, fonts and references to other nodes are left out, since the node does not give them back as the file spelled them, and so are nodes that code made, which the editor's scene does not have. A node the editor changed with `setField` is sent whole again. The editor shows the values in its inspector and hands the same list to its own player as `setFields`, so the scene view draws the game's world through the editor's camera, with the selection and the handles working on it, without a second window or a second renderer in the game. What code does inside a node, such as the cubes a `CubeField` makes, is not in that scene. When the game's active scene changes, including its first, it says `sceneChanged` with the scene's name, so the editor can show that scene: `PlayRunner` follows the scene through `BootObserver.sceneLoaded()`, which is also why the values it reports are of the scene on screen and not of the one that was opened. A node can show what code does to it by making that a field: the sandbox's `CubeField` works out how far each cube has turned from an `age` field, which the running game advances and the editor's own copy of the scene is given.
