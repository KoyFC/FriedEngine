# Scene files

A scene can also be data. `fried.scene.serialization.SceneLoader.register(name, assetPath, renderer)` registers a JSON file under the game's assets as a scene `SceneManager` can load, and `SceneLoader.build()` turns the parsed data into a `Scene`. The file is written by the editor and only ever read here, so there is no saving on the engine's side. It holds a `version`, a `name`, an optional `camera` naming a node, and `nodes`, the children of the root in draw order. Each node has a `type`, a stable `id`, an optional `name`, an optional list of `children`, and every other key is a field of a class in its chain. Ids exist because names are not unique, and `Scene.findById()` and the typed `Scene.getById(id, Type)` are how game code reaches a node a file created, to give a button its `onClick`, which a file cannot hold. A file of another `version` is refused with a message that says scenes are rewritten by hand, since there is no converter: the version is 2.

```json
{ "version": 2, "name": "Sandbox", "camera": "camera", "nodes": [
  { "type": "Camera", "id": "camera", "x": 320, "y": 240 },
  { "type": "Player", "id": "player", "x": 288, "y": 160, "texture": {"root": "game", "path": "sprite.png"},
    "children": [ { "type": "Collider", "id": "player-hitbox", "width": 32, "height": 96 } ] } ] }
```

Nodes are described, not reflected. A subclass of `Node` marked `@:serializable` gets a static `describeNode()` from the build macro `NodeBuilder`, which returns a `NodeType`: its name, the name of the nearest serializable class above it, the fields it declares itself, and how to create a node, assign fields to one and read them back. `create`, `assign` and `read` cover the fields of the whole chain, so a `Sprite`'s data may set a `Node2D`'s `x` as well as its own `texture`, and `fields` holds only the class's own, which is how an inspector shows one section per class. Every public, writable `var` of a supported type is a field: `Int`, `Float`, `Bool`, `String`, `Color`, `FlipMode`, `Rect`, `Texture` and `Font` as asset references, and any `Node` class as a reference to another node of the scene, which a file spells as that node's id. A reference stays null while the nodes are being built and the loader assigns it once all of them exist, so a node cannot use one in its constructor, only from `ready()` on. Functions and read-only properties are not fields, and `@:noSerialize` leaves one out by hand. A class field named `type`, `id`, `name` or `children` is a compile error, since a file's node already uses those keys. Constructor parameters are matched to fields by name and a required one with no field is a compile error, so a node that a file could not build never compiles as serializable. Assignment goes through the property, so a setter such as `Camera.zoom` still runs. A scene may use only the nodes `Builtins` lists and the ones a game adds with `NodeRegistry.register()`, because Haxe never types a class only a file names. `SceneLoader.load(assetPath, renderer)` builds a file's scene without pushing a layer for it, for a game that pushes its own layers, and what a file cannot know, such as a node that needs an `InputAction`, is set in code after it loads. A position taken from the view is a `Control`'s anchors, which the editor sees too.

An asset reference is `{"root", "path"}`, and a font adds `"size"`, resolved through `Filesystem.resolveAsset()`. A file that is wrong fails at load with the node and field in the message.

A scene has no per-platform values: a node that behaves differently on a platform says so in its own code, by asking `Application.platformName`.

A scene file is built whole before any node is readied: every node and reference exists, and then `ready()` runs on each, children before parents, so a node's `ready()` can read the rest of its scene. `SceneLoader.build()` can skip that for the editor, which only looks, so a node that draws must not need `ready()` to have run. A `Scene` knows the size of the view it is drawn to (`viewWidth`, `viewHeight`), so a node reads it from there instead of holding a `Renderer`. `SceneManager.loadAdditive()` loads a scene on top of the active one, such as an interface over a level, and loading another scene unloads it.

## Instancing a scene

An entry with an `instance` key, `{"id": "player", "instance": "player", "x": 40}`, puts another scene file in the tree as one node. `instance` names a scene the way `startScene` does, and the entry has no `type`: the node is the instanced file's root, and every other key of the entry overrides that field of the root, `name` included. An entry cannot have children. Only a file with exactly one top-level node can be instanced, its `camera` is ignored, and its root cannot itself be an instance entry. A scene that ends up instancing itself fails at load, naming the chain.

The ids of an instanced file belong to the instance, which is how two instances of one file never clash and how a file's own references keep meaning its own nodes. They are not in the outer scene's `findById()`: the instance's root has the id the entry gave it, and `instance.getById("hitbox", Collider)` reaches a node inside. An override of a reference field, such as `"wall": "wall"`, names a node of the outer scene. A node meant to be instanced should not require such a reference in its constructor, since its own file cannot give one.

Code does the same with `PackedScene`: `PackedScene.load("player").instantiate()` builds the root with its subtree and no id, ready to be added to any node with `addChild()`, and it is readied when it joins a scene. The file is read once and kept. The editor shows an instance as the one node it is, with the box of everything inside it.
