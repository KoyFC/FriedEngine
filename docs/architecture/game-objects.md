# Game objects

A `fried.scene.GameObject` is a name, an id, an `active` flag and a list of components, and exactly one of them is its `Transform`. A scene is a tree of transforms under a hidden root, and what a thing is comes from the components it carries: a game extends `Component` and overrides what it needs, as Unity's `MonoBehaviour` does. The transform decides where the object is and who its parent is. `Transform2D` is placed by a position, a rotation in degrees and a scale relative to its parent, and a `SpriteRenderer`, a `Camera` and a `Collider` sit on one. `RectTransform` is placed against its parent's rectangle, and a `Label`, a `TextureRect`, a `Button`, a `TouchButton`, a `VirtualJoystick` and a `UIDocument` sit on one. `Transform3D` is placed by a position, a rotation in degrees about each axis and a scale on each, relative to the nearest `Transform3D` above it, applied about z, then x, then y, as Unity does, and a `MeshRenderer`, a `Light` and a `Camera3D` sit on one; a 2D transform under it is placed as if it had no parent. A plain `Transform` has no position and only holds the hierarchy, which is what an object that only groups others uses. A component that needs a kind of transform asks for it in `awake()` with `need(Transform2D)`, which fails with a message that names the object when it is missing.

A behavior that acts on another thing is a component on the same object, or on one above it, found with `getComponent()`, `getComponentInParent()` or `getComponentInChildren()`, which is what a scene file can hold and the editor can show. An earlier model gave every object a list of components with no hierarchy, and a later one replaced it with a tree of nodes whose classes were the types; this one keeps the tree and moves the types into components. The hierarchy belongs to the transform, so `transform.setParent()`, `children`, `getChild()` and `find()` are where it is changed and read.

Components are not stored as data in arrays. Each one is a Haxe object with its own fields, because hxcpp has no value types and an array of structs would only be an array of pointers, and because the engine's hot paths already live in native stores: the 2D transforms, the collider grid and the tilemaps. An object is three objects for the collector where a node was one, which is the cost of the model; the heap of the sandbox's 3D scene on the DS is what decides whether it has to be made smaller.

A drawn size belongs to the component that draws: a `SpriteRenderer` takes the texture's dimensions, or those of its source region, and multiplies them by the world scale, so no stored size can disagree with a scale.

`ComponentBuilder` is a build macro that runs on every subclass of `Component`. For a class that declares `update()`, `draw()` or `onEvent()` it overrides `hookFlags()` to say so, and a scene keeps one list per hook, rebuilt by a single walk of the tree only when the tree changed: an object entered or left it, a component was added or removed, or a priority changed the order of events. A frame calls just the components that have the hook, so hundreds of plain objects, such as the parents of a pool that are switched off, cost nothing per frame. The hooks are private and the calls are opened to the scene with a targeted `@:allow`, so a component overrides a hook and the frame calls it, but game code cannot call it by hand.

A component runs only when it `isOn`: its own `enabled` is true and its object is `activeInHierarchy`. `active` of an object and the `activeInHierarchy` it caches work as `active` did for a node: a change rewrites the cache with one walk of that subtree, the frame loops, `Physics` and the event walk read only the flags, and an inactive object switches off its children and their colliders with it. There is no `visible`: a component that draws is hidden with `enabled = false`, an object and everything under it with `active = false`, and a whole `Canvas` with `enabled = false` on it.

A `Scene` updates every component and then draws every component, in two passes rather than one. All movement therefore happens before any drawing, so an object that another moved in the same frame is never drawn where it used to be. `update(delta)` receives the seconds the frame took, the value `Time.deltaSeconds` holds, so a movement takes its step from its own argument and not from a global.

The tree changes at once and the lists are refilled before the next pass, so a component can add or destroy objects from inside `update()`; the loops skip a component whose object has left the scene. `awake()` is called when a component joins an object, and `start()` once, when its object first enters a scene, children before their parent. A scene file builds its whole tree first, so every object and reference exists when `start()` runs, and the editor player never starts them. An object made in code starts its components as soon as it joins a scene, which is what spawning at run time relies on. `destroy()` detaches an object, clears its scene and calls `onDestroy()` on each component of its subtree, children first.

A `Transform2D` and a `RectTransform` cache their world position, rotation and scale. Setting a field, or moving an ancestor, marks the transform and those below it dirty, and the next read works the value out again. A parent with no rotation and a scale of one, which is nearly every parent, takes additions only, since the DS has no FPU. Otherwise the local position is scaled and rotated by the parent's world values and added to its position. A `Transform2D` that is in a scene does not work this out in Haxe: its position, rotation and scale live in a native store (`native/scene/`, in Haxe `TransformStore2D`) under a slot the transform holds for as long as it is in the scene, and the store works the world values out from the parent's. On the DS the store keeps them in 16.16, which limits a position to about 32768 pixels either way, and turns through a sine table, so an object deep in a rotated hierarchy can sit up to a twentieth of a pixel from where doubles would put it; everywhere else it keeps floats. What draws a sprite and what bounds a collider read the store alone, and the store is brought up to date only when one of them asks. The `Single`s `worldX` and the others are filled in from it only when they are read, which is what the world cache above guards. A transform outside a scene, or a `RectTransform`, whose layout reads the cache, is still worked out in Haxe. A slot freed when a transform leaves the scene is reused only after the frame's draw queue has been flushed, since records of that frame may still name it.

A 2D position, size, angle or scale is a `Single`, a 32-bit float, on every platform: half the memory of a `Float` for every transform, slot and draw record, and on the DS a cheaper operation. That holds only while the arithmetic stays in `Single`. Haxe types `a * b` of two `Single`s as `Float`, so a local variable that holds the result needs `:Single`, and `/`, a literal such as `0.5`, `Math` functions and a `Float` operand turn the operation back into a double, which is slower than if nothing had been converted. Write `* HALF` with `static inline var HALF:Single = 0.5` instead of `/ 2`. `Time.deltaSeconds` stays a `Float`. A field that is a `Single` is saved in a scene file as the shortest decimal that reads back as the same single.

A `RectTransform` is placed against its parent's rectangle, with the vocabulary of Unity's interface: anchors as fractions of the rectangle, a pivot, an offset, and insets for an axis whose two anchors differ and the object is stretched between them. The parent's rectangle is a parent `RectTransform`'s; a parent `Transform2D` gives a point at its position, so a label under an object follows it with its offsets as a position; under the root, or a plain `Transform`, it is the view. An object's size is what its renderer says, such as a `Label`'s measured text or a `TextureRect`'s picture, scaled to fill a stretched axis, and otherwise the `width` and `height` of the `RectTransform`. The renderer registers itself as the size source of the transform, which is how a layout reads a size without knowing which control it is. `below` stacks an object under another with the offset as the gap. Layout is part of reading the world position, so it happens again only after something it depends on changed: its own fields, its parent's rectangle, the object `below` names, a `Label`'s text or font, or the size of the scene's view, which `Scene.setView()` walks the tree for once when it changes. A loop of `below` is reported once and broken. The editor measures the box it selects by the same sizes, so a layout and a selection never disagree.

A `Canvas` on an object marks it as the root of a part of the scene that is drawn in screen space: what is under it ignores the scene's camera, is drawn after the world and its meshes, and gets input before the world does, which is how one scene holds both a level and its interface. Canvases are ordered by their `layer`, a component's own `priority` only orders it inside its layer, and disabling the canvas hides everything under it and keeps input from it. A scene keeps the draw and input lists of each canvas apart when the tree changes, so a frame still never walks the tree. The editor's scene view draws a canvas through the camera, so the interface sits in the world where it can be picked and moved; the Game tab and a running game draw it in screen space.

`Renderer2D` is the base of everything that is drawn on the plane: it holds the `priority` that orders it among the others and the size it measures itself by. A priority change marks the order of events dirty, as it did for a node.

`Button` is the one component the engine ships that takes input, which is why components have an `onEvent()` hook next to `update()` and `draw()`. The hook gets the event and nothing else: a component never holds a `Renderer` or a layer, and reads the size of its view from its scene. A scene receives the events of the layer it is in and hands each one to the components that have the hook, top first: the tree order reversed, then stable-sorted by priority, so the button drawn over another is the one pressed. The walk stops at the first component that sets `handled`. A button is held by the mouse or by one finger on the front touch device, shows as pressed while that pointer is over it, and calls `onClick` when the pointer is released over it; released elsewhere, it lets go without a click. Its state is `isPressed` and nothing more: no focus, so a gamepad cannot reach it yet. It hit tests through its scene's camera, so it works in world space as well as on an interface scene without one.

A `TouchButton` is a round button that holds an input action while a finger is on it, so a game reads it as it reads a key bound to that action. Its circle fills the shorter side of its rectangle and is drawn with triangles, so it needs no texture on any platform. The left mouse button stands in for a finger, which is how it is tried on a computer. With `isPassBy` a finger that slides onto it presses it and one that slides off lets it go, and `platforms` says where it is drawn and pressed: platform keys such as `android web`, plus `auto` for wherever a finger touches the screen the game is drawn on (`Input.isTouchOnDisplay`). Empty means `auto`, which leaves out the DS and the 3DS, whose touch screen is another screen, and the calculator; a browser or a computer is named in the list when its mouse should get the control. The editor's scene view always draws it, so it can be placed, while a game the editor plays follows the list for the platform being previewed. `onPressed` and `onReleased` are there for what is not an action.

A `VirtualJoystick` is a stick on the screen that sets one vector2 action to where its tip is, from -1 to 1 on each axis with up negative, the way a gamepad's stick reads. It rests at the middle of its rectangle, drawn as two circles, and the tip is held inside the base. Where Godot's `VirtualJoystick` presses four actions, this one sets a single vector2 action, so a game that moves with a stick, the keys and the D-pad reads one action for all of them. `deadzone` is the share of the base's radius the tip moves before anything is read, `isDynamic` moves the base to where a finger lands anywhere in the rectangle, `isHiddenUntilTouched` draws it only while held, and `platforms` chooses where it shows, as for the `TouchButton`. The left mouse button stands in for a finger.

## Moving from nodes

Scenes of the earlier model are version 2, and `fried_import migrate-scenes <project>` rewrites them as version 3 (see [Scene files](scene-files.md#migrating-a-project)). The classes of a game that extended a node become components: `ready()` is `start()`, `destroyed()` is `onDestroy()`, `findParent(T)` is `getComponentInParent(T)`, `addChild()` is `transform.setParent()`, and `visible` is `enabled` on the component that draws or `active` on the object. A `Sprite` is a `SpriteRenderer`, a `CanvasLayer` a `Canvas`, a `MeshInstance3D` a `MeshRenderer`, a `DirectionalLight` a `Light` and a `PackedScene` a `Prefab`. One thing changes in behavior: a node hidden with `visible` hid everything under it, while `enabled` hides only its own component.
