# Tilemaps

A `fried.scene.Tilemap` is a `Node2D` that draws a grid of tiles cut from one picture. Its fields are the `texture`, the size of a tile in the picture's pixels (`tileWidth`, `tileHeight`), the size of the map in tiles (`mapWidth`, `mapHeight`) and `cells`, which is how a scene file keeps the tiles: one line for each row, and in it the number of each cell separated by spaces. 0 is no tile, and any other number is the tile's place in the picture counting along its rows from 1. Its position is its top left corner, its parent's scale scales it, and it is never turned.

The grid does not live in Haxe. A tilemap in a scene owns a map in the native store (`native/scene/tilemap.cpp`), made when it enters the scene and released when it leaves it or any of its fields changes, and filled by one pass over `cells` that allocates nothing. The map is one array of 16-bit cells, so a 64 by 32 map is 4 KB however many tiles it shows. `getCell()` and `setCell()` read and change that array while the game runs, and do not touch `cells`.

A tilemap draws one command in the queue, not one for each tile. The record (`RECORD_TILEMAP`) names the texture, the map and the transform slot that places it, and the renderer works out which cells the screen shows from the camera and draws only those, so a large map costs what its visible part costs. Every renderer but the DS's 3D engine decodes the record into one texture draw for each visible tile (`draw_batch.cpp`). The DS draws each as a quad in 16.16 fixed point (`drawTilemapRecord` in `renderer_nds.cpp`): an opaque tileset opens one polygon list and sets one color for the whole map, and each edge is worked out once for the row or column that shares it, so a tile's neighbours have the same edge numbers and no seam opens between tiles at any scale or camera position. A translucent tileset, or a view of more than 96 tiles across or down, draws tile by tile through the texture record's path instead.

The cost on the DS is about 3 microseconds a tile, so a screen of 16 by 12 tiles takes 0.6 ms of a 16.7 ms frame (1.4 ms before the edges were shared). A map drawn by the DS's tile layers would cost nothing a frame, but needs a tileset converted to 4 or 8 bits a pixel at import, which the engine does not do yet. Measure it with the `tiles` bench (`bench/tiles.hxml`), see [Profiling](../development/profiling.md).

With `isSolid`, every cell that holds a tile also stops what is on the `collisionLayer` below it. The native layer covers the cells with rectangles (`fried_tilemap_build_solid()`: a run along a row, grown down while the rows below hold the same run), and the tilemap adds one `Collider` child for each, which Physics finds like any other, so a wall of forty tiles is one box. On the DS, a 32 by 24 level of walls and bars with forty movers querying around themselves took 0.5 ms less to update (4.46 ms against 5.00 ms) with the merged boxes than with a collider for each cell. The boxes are made when the map is, and `refreshColliders()` makes them again after a run of `setCell()` calls that changed what is solid.
