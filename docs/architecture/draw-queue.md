# The draw queue

Drawing never reaches the renderer directly. A component's `draw()` submits a command to `fried.graphics.DrawQueue`, the loop flushes the queue between the update callback and `present()`, and the queue sorts before dispatching to the renderer. That is what separates the order things are drawn in from the order the code emits them in. Before the queue existed those two orders were the same thing, and changing what went on top meant moving lines.

The sort key is the triple of layer index, draw priority and submission index, ascending, so a smaller value is further back and equal ones keep the order they were submitted in. The submission index is unique within a frame, which makes the triple a total order: two commands never compare equal, so no sorting algorithm can produce a different picture from another. The guarantee is in the key rather than in the stability of an implementation.

Commands come from a pool that is reused between frames instead of one allocation per sprite per frame, since the cost that matters is GC pressure on a console. Each command copies the values it was given, including the contents of a `Rect` and the points and colors of a batch of triangles, so mutating a rect or an array after submitting cannot alter a command already queued. The pool grows to the largest frame the program has drawn and stops there.

The draw color is ambient renderer state that `clear()` also reads, so the queue takes note of it before dispatching and puts it back if any command changed it. Otherwise the last rectangle of one frame would become the background of the next. Flushing also happens when there is no renderer, minus the sorting and the dispatch, because a queue that only drained when something could draw would grow without a ceiling.

The queue is static, like `Time` and `Input`, and each command records the renderer it was submitted for. `DrawQueue.currentRenderTarget` names that renderer, `Scene.draw(renderer)` sets it for the length of a pass, and the loop points it at the first renderer before the update callback so a program with one window never has to know the field exists. A flush sorts once and then walks the commands once per renderer, so ordering is decided globally and dispatch is filtered per target.

A frame's sprites, rectangles and outlines do not reach the renderer one call each: the walk writes them as records into two arrays, eight integers and five doubles to a record, and hands the whole run to the renderer in one `fried_renderer_draw_batch()`, which a command of another kind (text, triangles, a mesh) ends. The camera travels as a record of its own, and the numbers in a record are the world's: the placement through the camera, which the draw queue used to work out in Haxe, is done natively, and so is a sprite's size: a `Sprite` or a `TextureRect` queues its scale, in a record of its own kind, and the renderer multiplies it by the size of the texture or of its region.

A `Sprite` that is in a scene queues no position either: its record, of another kind again, names the slot its transform has in the native store, and the renderer reads the place, scale and angle from there when it draws the batch, in fixed point on the DS, so the numbers are not copied through the record arrays or converted a second time. Every backend but the DS decodes the records back into the calls it had before, with the same arithmetic in the same order (`draw_batch.cpp`, which multiplies a scaled size as the sprite did), so what it draws is unchanged.

The application flushes it but does not own a scene: framing a frame is the loop's job, while a scene is game content and nothing about a scene says there can only be one. A game drives its scenes through the layers of a renderer, or by hand from the update callback. One consequence is worth knowing: anything drawn by calling the renderer directly from that callback is drawn before the flush, so it ends up underneath everything queued, whatever priority the queued commands carry.

`SpriteRenderer` and the other components live in `fried.scene` rather than in `fried.graphics` so that the dependency runs one way. The scene knows what graphics are, and graphics know nothing about components, which is the same rule that keeps windows from knowing that renderers exist.

A draw priority is a single flat number within its layer, not inherited from a parent, and a game sets it on the component at any time, including from a component in the middle of a frame.
