# Text

`Label` is the text component the engine ships, and it holds no texture. Each draw submits the string to the queue, and the renderer draws it a glyph at a time from an atlas: one texture per font and renderer, built on the first text drawn there, holding every glyph it has rasterized. Printable ASCII goes in when the atlas is built, and any other character is rasterized the first time it is drawn and stays. A string that changes every frame therefore costs layout and quads, never a texture. Rendering a whole string to a texture instead, which is what the engine did before the atlas, meant an SDL_ttf render, a format conversion, an allocation and an upload per change, all on the CPU, which on a 3DS is a 268 MHz ARM11.

The glyphs are rasterized in white and tinted when drawn, so one atlas serves every color, and the layout that places them is the one `Font.measureWidth()` measures with, so a box sized from it fits the line exactly. That layout is SDL_ttf's per glyph metrics plus kerning, which can differ by a pixel from what it would render for the whole string. Both are cached per font on the engine's side, so a frame makes no SDL_ttf call at all once its glyphs are in the atlas. That is not an optimization but a requirement: SDL_ttf caches 256 glyphs in slots picked by glyph index modulo 256, so asking it every frame about a line with two glyphs sharing a slot reloads both through FreeType, over and over. NunitoSans has eleven such pairs within ASCII, and asking for kerning per pair per frame took the sandbox from 60 FPS to 26 in Azahar. The atlas side grows with the line height, from 256 to 1024 pixels, the most the 3DS takes; a character that no longer fits is left out rather than failing the draw. Atlases go with their renderer, released by `fried_renderer_destroy()` before the renderer itself, and with their font. The font file itself is read into memory whole when it is loaded, because FreeType otherwise reads it a glyph at a time, and on a 2DS each of those reads goes through the romfs to the SD card: that alone kept the sandbox's first frame back 5.1 seconds from `main()`, against 0.6 with the file in memory.

An atlas is rasterized at the size its font covers on that renderer's screen, not at the size the text is laid out at. With a display scaled by 1.5, a 16 pixel font is rasterized at 24 and drawn back at 16 logical pixels, so the glyphs land one texel per output pixel instead of being enlarged or shrunk by the nearest filter, which had left text blocky when scaled up and unreadable when scaled down. When the scales of the two axes differ, as under `stretch`, the smaller one is used, since stretching a glyph costs less than dropping rows of it. The layout stays at the font's own size, so `measureWidth()` and `lineHeight` do not depend on the screen. The atlas opens its own copy of the font at that size from the file already in memory, and is rebuilt when the scale changes, such as when the window is resized. Where the display shrinks the game, as `height` does on a small screen, a font laid out at 16 pixels is rasterized at 6 and cannot be read, and the layout stays at the font's own size on purpose, so the world keeps its view. `Renderer.pixelScale` says how many output pixels a logical one covers, and `Renderer.legibleSize(size, screenPixels)` gives the logical size that is at least that tall on the output, which the game asks for when it creates its font. A font in a scene file asks the same with an optional `minScreenSize` beside its `size`.

`textWidth` and `textHeight` come from the font and are measured once per change of `text`, `font` or `maxWidth`, so a size is there before the first frame: the sandbox sizes its hint panel around a label that has never been drawn. One `Label` is one line unless it has a `maxWidth`: then it is broken between words into lines no wider than that, and a word wider than it gets a line of its own. Its size is that of the whole block, and the editor shows the same block. Each line is submitted on its own, so a broken text is not meant to be rotated.
