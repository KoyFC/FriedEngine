# Layers

A `fried.Layer` is a name, an enabled flag and three hooks a game overrides: `update(delta)`, `draw()` and `onEvent()`. `fried.scene.SceneLayer` is the only one the engine ships, and it barely has a body: it holds a `Scene` and forwards the three hooks to it. So the common case, a world with an interface over it, is two pushes, and a layer can still draw what is not a scene: `sandbox/src/DebugOverlay.hx` draws its buttons through a scene and its readout straight to the queue from its own `draw()`. Making a layer *be* a scene would have closed that door to save those few lines.

A `SceneLayer` does not own its scene. The game created it and the game destroys it, so removing a layer takes down the presentation and leaves the content alone.

The stack belongs to the `Renderer`, not to the application. A layer stack answers "what is in this window, and in what order", and that question has one answer per window: the sandbox drew three scenes before layers existed. One global stack would have made every layer carry the renderer it draws to, which is the field the stack already is. Putting it on the renderer also hands event routing its answer for free, since an input event carries the window it happened in and a renderer knows its window.

The layer index is the first term of the draw queue's sort key, ahead of draw priority, so a layer is above another by construction rather than by agreement. That is what it buys over arranging the same thing with priorities: the sandbox used to give its interface nodes priorities of 10 and 20 to keep them off the world, which is a number picked against every other number in the program, and a growing world could have walked into it. Priority itself did not change, and now orders within a layer, which is the scope it reads as.

A node or layer may also override `fixedUpdate(delta)`, which the loop runs a fixed number of times a second however long the frames take, before the frame's `update`. `Time.fixedStepsDue()` adds the frame's delta to an accumulator and says how many steps of `Time.fixedDeltaSeconds` it holds, which is the step every `fixedUpdate` is given. At most three run in a frame, and time still owed after that is dropped, so a slow frame never makes the next one slower by running more steps to catch up, and a frame a hair short of a step still runs it. `Project.physicsRate()` reads `physicsRate` from `project.fried`, 60 when it says nothing, and `Bootstrap` hands it to `Time.setFixedRate()`; a game with its own `main` does the same. A frame can run no step or several, so input is read in `update`, where a press is seen once, and left for the fixed step as a velocity. The hook has a bit of its own in the flags `NodeBuilder` writes, so a scene calls only the nodes that override it.

The loop updates every layer of every renderer and then draws them all, in two passes, for the reason `Scene` already does it: a layer that reads another while drawing should see the state the frame settled on rather than a half-updated one. A disabled layer is skipped by all three hooks, so turning a pause menu off costs a flag instead of a push and a pop. Adds and removals are deferred while a walk is in progress and immediate otherwise, which is the rule `Scene` already applies to its nodes, and removals are applied before adds so a layer taken off and put back inside one walk ends up in the list once rather than twice. The opposite order cancels out instead: a layer pushed and then removed inside one walk is dropped from the pending adds, since it never made it into the list and there is nothing to take out of it. The walk a change arrives during finishes over the list it started with, so a layer removed from another layer's `update()` still takes that frame's turn and is gone from the next walk, and a layer pushed there is drawn that frame before it has ever been updated. Both are what a scene does with a node created or destroyed mid-pass, and one rule across the two is worth more than a frame of latency in either direction. Each of the three walks applies what is pending before it starts, so a removal asked for while events are being propagated takes effect on the next event rather than at the end of the frame.

Events walk the stack from the top down, which is the reverse of the draw order, because the thing drawn last is the thing the click landed on. A layer that sets `handled` ends the walk, and the walk is what gives `handled` its meaning: `fried.Application` stops at the first layer to claim an event and the layers below never learn it happened. The sandbox's interface layer takes a click inside its panel, and the world layer underneath never logs that one, with neither layer knowing the other exists.

An event that carries a window only reaches the stack of that window's renderer, which is why the sandbox's layers test nothing about which window they are in. Keyboard and mouse events carry one, because SDL tags them with the window that had focus. A gamepad event carries none, so it walks every renderer in turn until a layer claims it, which with a single window is exactly focus routing. Tracking focus for the single case of a gamepad was not worth the state it would add.

What a layer cannot do is take an input away from the polled API, which is the trade-off the input section describes: a layer consumes a key press, and a node that asks `Input.isKeyPressed()` in the same frame still sees it.
