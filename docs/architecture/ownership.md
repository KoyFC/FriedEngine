# Ownership in the runtime

`fried.Application` owns the SDL lifecycle, the renderers and the game loop. `fried.Window` is only a window: it has no renderer field and nothing in it knows that renderers exist. A renderer is built from a window and owned by the application, so the two are created and destroyed separately, and a window may exist without one. The loop clears every renderer, runs the update callback, then presents every renderer.

That is the opposite of coupling them the way an engine usually does, where a window creates and owns its renderer. Keeping the application as the owner is what lets a window exist without one, and it means a second window, on hardware that has one, costs a collection rather than a change of layer. `fried.Window` already tracked its instances in a map and routed events per window before any of this, so the window side needed nothing.

How many windows a program may open is the platform's answer and not the game's. `FRIED_MAX_WINDOWS` in `native/platform/window.h` carries it, and `fried_window_create` refuses past it instead of letting SDL fail further down. A console's screens are fixed hardware: the Vita and the Switch have one, and the 3DS has two, each a window, which is why the limit is per platform rather than a choice the game makes. Haxe reads it as `Window.maxCount`, so a game can open the second screen only where there is one. The limit is checked on every target, desktop included, so a game that opens one window too many finds out on the development machine rather than after installing on a devkit.

The size of a window is the platform's answer on a console for the same reason. `fried_window_create` takes it from the screen the window lands on and ignores the size the game asked for, which only sizes the window on desktop. Without that, each SDL port did something different with a smaller window: the Vita drew it unscaled in a corner of the screen, the Switch stretched it over the whole screen, and on the 3DS the window kept a size its screen does not have, which is what touch positions are scaled by.

The position follows the same rule. `Window.x` and `Window.y` read and move the window on desktop, and on a console, where the window is the screen, they stay 0 and setting them does nothing. `Window.onMove` reports a move however it came about, the game's own `setPosition` included. The sandbox moves its window with Shift and the arrow keys.

Textures are owned by the renderer rather than by the game, and the cache that holds them lives on the `Renderer` instance. `Texture.from(renderer, path)` returns the same instance for the same file on the same renderer, so a texture used by ten sprites is one `SDL_Texture`, and destroying a renderer destroys every texture that belongs to it. A game therefore loads what it needs and writes no teardown list for it.

The cache cannot be keyed by path alone, and the renderer parameter is what makes that work. An `SDL_Texture` belongs to the renderer that created it and cannot be drawn by another, so a cache shared across renderers would answer the second renderer with the first one's texture. Keying it per renderer makes that unrepresentable rather than merely discouraged.

`destroy()` stays public, so a game can free a texture it is done with before its renderer goes. Destroying a texture drops it from the cache too, so a later `from()` on that path loads a new one instead of handing out a destroyed instance. What the cache does not do is count references, so two callers that share a path share the consequence if one of them destroys it. That is a guard rail rather than a sandbox, the same way the asset roots are.

Fonts and sounds follow the same rule with a different owner. `Font.from(path, size)` and `Sound.from(path)` are cached and torn down by `Application.shutdown()`, because neither depends on a renderer: a `TTF_Font` renders to a surface and a `Mix_Chunk` is decoded audio, so their lifetime is the program's rather than a window's. The font key carries the size, since one file opened at two sizes is two `TTF_Font`s. Both are destroyed before the native shutdown, which calls `TTF_Quit()` and `Mix_CloseAudio()` and would pull the ground out from under them.

`Music` deliberately keeps its constructor and is not cached, and a game still destroys its own. SDL_mixer has a single music stream, and `native/audio/music.cpp` tracks which id is currently on it, so `playing` and `paused` answer for the stream rather than for the object. Sharing an instance would buy nothing, since a game holds few tracks and `Mix_LoadMUS()` streams the file instead of decoding it into memory the way `Mix_LoadWAV()` does, and it would cost something, since destroying a shared instance halts the stream for whoever else was playing it. A sound is the opposite on both counts: the playback state lives in the channel rather than in the chunk, so the same chunk can play on eight channels at once, and the duplicates a cache removes are real.

`Renderer.destroy()` destroys its own textures before destroying itself, and carries the same `@:allow(fried.Application)` its constructor already did, so the one type that creates renderers is the one type that destroys them. That ordering is therefore structural rather than conventional. It matters because SDL frees a renderer's textures along with it, and `HandlePool` recycles ids, so a pool left holding freed pointers would eventually serve one of those ids for an unrelated texture and draw the wrong thing rather than crash. A sweep in `fried_renderer_destroy()` would be unreachable code, since no path reaches the renderer without passing through the application first.

The loop clears before the update callback and presents after it, so drawing code is only ever the middle of a frame that is already framed for it. A renderer is optional; with none, the loop runs exactly as it did before that step existed.

`vsync` is read back from SDL after creation rather than remembered from what was asked for, because a driver may refuse it and a loop that skipped its fps cap believing it had vsync would run unbounded. `targetFps` is ignored only while *every* renderer has vsync, since sleeping on top of vsync would push the next frame past the following vblank and halve the rate. One renderer without it is enough to put the cap back, because that renderer's `present()` does not block and nothing else would bound the frame.
