# 3D

3D is worked out on the CPU in Haxe and drawn as 2D triangles, so it needs nothing from a platform beyond `fillTriangles()`, which every backend already has, unless the renderer draws meshes itself, which the DS, PC, Switch, Vita and 3DS renderers do and the web build does not. It lives in `fried.graphics3d`, apart from `fried.graphics`, because the line between them is where the 3D ends: `fried.graphics3d` works out which triangles to draw and where, and `fried.graphics` draws them like any other shape.

A scene's `camera3D` (the `camera` key of a scene file may name a `Camera` or a `Camera3D`) draws every `MeshInstance` of the scene in one pass, `MeshPass`, after the scene's 2D nodes. `Scene` finds the meshes and the lights through the bits 64 and 128 of `hookFlags`, as it finds colliders. The pass turns each mesh into the camera's space, drops each triangle that faces away, shades the rest by how squarely each faces into the first `DirectionalLight` that is shown (a scene with none leaves its meshes unlit), sorts the triangles of all the meshes together, farthest first, and submits them to the queue as one batch at the camera's priority. The pass does not go through the scene's 2D camera, so panning and zooming the world leaves it where it is. One color per triangle is what flat shading needs and what the fx-CG50 can fill without interpolating. The space is left handed, with y up and z going away from the camera, and rotations are applied about z, then x, then y, as Unity does.

A `MeshInstance` draws one of the built-in shapes, `Cube`, `Plane`, `Pyramid` or `Sphere`, each one unit across, in a `color`, or the `Mesh` the code gives it. The meshes are made once for each shape and color and shared by every instance that uses them. The sphere is low in polygons (80 triangles) because the DS draws 2048 polygons a frame, and the plane is cut into a 16 by 16 grid, since triangles are ordered by their average depth and one large pair would be ordered as a single point against whatever stands on it.

Where the triangles are drawn as 2D there is no depth buffer, so the order is the painter's: triangles are sorted by the average depth of their corners, cut into 65536 steps between the nearest and the farthest and sorted a byte at a time, since a comparison sort of a scene's triangles took longer than the rest of the pass. That is exact for a single convex mesh such as a cube, and wrong for triangles that cross or interlock. A triangle crossing the near or the far plane (`Camera3D.near` and `far`) is cut at it, which leaves a polygon that goes as a fan of triangles, and a mesh whose bounding sphere is wholly outside either plane or a side of the view is not turned at all. The DS's hardware clips and culls the sides and the near plane on its own, and its way of ordering meshes by depth has no far plane, so it draws them to any distance. The viewport is the whole view of the scene, and nothing is clipped to it.

A renderer can draw meshes itself instead, which the DS's top screen, the SDL renderer on PC, the Switch and the Vita, and the 3DS's do. One Haxe build serves every platform, so `MeshPass` asks the renderer at run time: where it draws meshes, the mesh is copied to it the first time it is drawn there (`graphics/mesh.h`), and each draw sends only the numbers that place it, the transform, camera (position and rotation), near and far planes and light as they are, written straight into the queue's command. The DS loads the camera's turn undone into its modelview matrix when a run of meshes begins, and sets the light under it, so the light is turned into the camera's space by the hardware. `mesh_none.cpp` says no renderer does, and the triangles are worked out as above. `Mesh.destroy()` frees the copy.

On PC and the Switch `renderer_sdl.cpp` asks SDL for its `opengl` driver, or `opengles2` on the Switch, whose GL is Mesa's over EGL, with batching on and a 24 bit depth buffer asked for by `window.cpp` before the window is made, and `mesh_gl.cpp` draws meshes in that same context, with a depth test, back-face culling, and the near and far planes of the camera. The environment can still name another driver, and where the context has no depth buffer or the program does not compile, the renderer draws no meshes and the CPU path above is used. A mesh is kept as its triangles, each corner with its face's normal and color, and uploaded to a vertex buffer the first time it is drawn, since the ids `Mesh` holds outlive the renderer's context. The vertex shader turns and lights each face as `MeshPass` does, to the same shades. SDL's own calls are flushed before a run of meshes, and the few pieces of state both use (the program, the array buffer, the vertex arrays, the viewport and the scissor test) are saved when a run begins and put back by `fried_mesh_sdl_leave()`, which everything that touches SDL in `renderer_sdl.cpp` and `texture_sdl.cpp` calls first, so SDL goes on knowing what it last set. The depth buffer is cleared as each run begins. On the Vita there is no GL. `renderer_sdl.cpp` names SDL's `VITA gxm` renderer, with `SDL_HINT_RENDER_BATCHING` on, since naming a driver turns SDL's batching off and unbatched, that renderer runs a whole GPU scene for every sprite and glyph, and the sandbox fell to a few frames a second. `mesh_gxm.cpp` draws meshes with GXM inside that renderer, through an SDL2 the engine builds from source (`cmake/vita_sdl2/`) with a patch (`sdl2-vita.patch`) that exports three calls: the renderer's GXM context and shader patcher, beginning a scene, and ending one, which also marks SDL's clip rectangle to be set again. SDL ends its scene whenever its queue is flushed, so after `SDL_RenderFlush` none is open, and a run of meshes is a scene of its own. A new scene starts with the depth at its far value, which is the depth clear, and with the stencil at 0, so the stencil test is set to always pass, SDL's clip being a stencil test it would otherwise fail. A change of view ends the scene and begins another. `fried_mesh_sdl_leave()` ends the scene, so SDL's next scene starts as it always does. The vertex shader is Cg compiled on the console by [`libshacccg.suprx`](../platforms/vita.md#requirements), which Sony's firmware does not carry and vitaGL games already put in `ur0:data/`; it is loaded from there, or from `ur0:data/external/`, and the app links the compiler's stub weakly so it starts without it. Without the module, or if a shader does not compile, the renderer draws no meshes and the CPU path above is used. The matrices are passed as rows, to leave no doubt about Cg's layout, and a mesh's vertices are in GPU memory made the first time it is drawn, drawn in chunks of up to 65535 corners with one shared index buffer. What it logged goes to `ux0:data/SDL_Log.txt`.

On the 3DS `mesh_citro.cpp` draws meshes with citro3d on the screen's own depth buffer, through a vertex shader (`mesh_citro.v.pica`, built by picasso and linked in) that turns and lights each face as `MeshPass` does, cut to whole bytes as the CPU does. `renderer_citro.cpp` calls `fried_mesh_citro_leave()` before any other draw, which puts citro2d's state back with `C2D_Prepare()`. citro2d draws every object at one depth and tests with `GEQUAL`, so the depth buffer is written to zero, with a quad that tests `ALWAYS` and writes no color, as a run of meshes begins and again as it ends, which leaves nothing the 2D that follows cannot draw over. The screen is mounted a quarter turn, so the clip matrix swaps x and y.

## Limitations

- Meshes are drawn as triangles, in painter's order, wherever the renderer draws none: the web build, the Vita without `libshacccg.suprx` in `ur0:data/`, and PC and the Switch when SDL has no OpenGL context with a depth buffer
- The Switch's backend has only been built, not run, and the 3DS's has only run in Azahar, not on a console
- The 3DS sorts meshes in the 16 bit depth buffer of its screens, so far-off meshes can flicker where they nearly touch
- Works on every platform except the fx-CG50, which keeps the `fillTriangles()` it has now and gets no further 3D support
- Games only use nodes, so a GPU backend can replace the pipeline later
- No per-frame allocations
