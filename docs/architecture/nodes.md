# Nodes

A `fried.scene.Node` is a name, an id, an `active` flag and a list of child nodes. A scene is a tree of them under a hidden root, and what a thing is comes from its class: a game extends `Node` or one of the engine's typed nodes and overrides what it needs. The classes form a chain. `CanvasItem` adds a draw priority, visibility and a world position that everything drawn shares, and under it there are two branches: `Node2D`, placed by a position, rotation in degrees and scale relative to its parent (`Sprite`, `Camera` and `Collider` are `Node2D`s), and `Control`, placed against its parent's rectangle (`Label`, `TextureRect`, `Button`, `TouchButton` and `VirtualJoystick`). `Node3D` is a third branch, placed by a position, a rotation in degrees about each axis and a scale on each, relative to the nearest `Node3D` above it; its rotation is applied about z, then x, then y, as Unity does, and a 2D node under it is placed as if it had no parent. A behavior that acts on another thing is a child node that acts on its `parent`, found with `findParent()`, which is what a scene file can hold and the editor can show. An earlier model gave every object a list of components and a transform component, with no hierarchy; the tree replaced it whole.

A drawn size belongs to the node that draws: a `Sprite` takes the texture's dimensions, or those of its source region, and multiplies them by the world scale, so no stored size can disagree with a scale.

`NodeBuilder` is a build macro that runs on every subclass of `Node`. For a class that declares `update()`, `draw()` or `onEvent()` it overrides `hookFlags()` to say so, and a scene keeps one list per hook, rebuilt by a single walk of the tree only when the tree changed: a node entered or left it, or a priority changed the order of events. A frame calls just the nodes that have the hook, so hundreds of plain nodes, such as the parents of a pool that are switched off, cost nothing per frame. The hooks are private and the calls are opened to the scene with a targeted `@:allow`, so a node overrides a hook and the frame calls it, but game code cannot call it by hand.

`activeInTree` and `shownInTree` cache what the ancestors allow. A change of `active` or `visible` rewrites them with one walk of that subtree, and the frame loops, `Physics` and the event walk read only the flags, never the chain of parents. A subtree stops with its parent: an inactive node switches off its children and their colliders with it.

A `Scene` updates every node and then draws every node, in two passes rather than one. All movement therefore happens before any drawing, so a node that another node moved in the same frame is never drawn where it used to be. With a single pass, tree order would quietly decide which nodes got a stale position. `update(delta)` receives the seconds the frame took, the value `Time.deltaSeconds` holds, so a movement takes its step from its own argument and not from a global.

The tree changes at once and the lists are refilled before the next pass, so a node can add or destroy others from inside `update()`; the loops skip a node that has left the scene. `destroy()` detaches a node, clears its scene and calls `destroyed()` on each node of its subtree, children first. `ready()` is called once per node, children before their parent, when it first enters a scene. A scene file builds its whole tree first, so every node and reference exists when `ready()` runs, and the editor player never readies them. A node made in code is readied as soon as it joins a scene, which is what spawning at run time relies on.

A `CanvasItem` caches its world position, rotation and scale. Setting a `Node2D` field, or moving an ancestor, marks it and the `CanvasItem`s below it dirty, and the next read works the value out again. A parent with no rotation and a scale of one, which is nearly every parent, takes additions only, since the DS has no FPU. Otherwise the local position is scaled and rotated by the parent's world values and added to its position. A `Node2D` that is in a scene does not work this out in Haxe: its position, rotation and scale live in a native store (`native/scene/`) under a slot the node holds for as long as it is in the scene, and the store works the world values out from the parent's. On the DS the store keeps them in 16.16, which limits a position to about 32768 pixels either way, and turns through a sine table, so a node deep in a rotated hierarchy can sit up to a twentieth of a pixel from where doubles would put it; everywhere else it keeps floats. What draws a sprite and what bounds a collider read the store alone, and the store is brought up to date only when one of them asks. The `Single`s `worldX` and the others give a game are filled in from it only when they are read, which is what the world cache above guards, and a node under no parent is its own world and never asks the store for them. A node outside a scene, or under a `Control`, whose layout reads the cache, is still worked out in Haxe. A slot freed when a node leaves the scene is reused only after the frame's draw queue has been flushed, since records of that frame may still name it.

A 2D position, size, angle or scale is a `Single`, a 32-bit float, on every platform: half the memory of a `Float` for every node, slot and draw record, and on the DS a cheaper operation. That holds only while the arithmetic stays in `Single`. Haxe types `a * b` of two `Single`s as `Float`, so a local variable that holds the result needs `:Single`, and `/`, a literal such as `0.5`, `Math` functions and a `Float` operand turn the operation back into a double, which is slower than if nothing had been converted. Write `* HALF` with `static inline var HALF:Single = 0.5` instead of `/ 2`. `Time.deltaSeconds` stays a `Float`. A field of a node that is a `Single` is saved in a scene file as the shortest decimal that reads back as the same single.

A `Control` is placed against its parent's rectangle, with the vocabulary of Unity's interface: anchors as fractions of the rectangle, a pivot, an offset, and insets for an axis whose two anchors differ and the control is stretched between them. The parent's rectangle is a parent `Control`'s; a parent `Node2D` gives a point at its position, so a label under a node follows the node with its offsets as a position; under the root, or a plain `Node`, it is the view. A control's size is what its class says, such as a `Label`'s measured text or a `TextureRect`'s picture, scaled to fill a stretched axis, and otherwise its `width` and `height`. `below` stacks a control under another with the offset as the gap. Layout is part of reading the world position, so it happens again only after something it depends on changed: its own fields, its parent's rectangle, the control `below` names, a `Label`'s text or font, or the size of the scene's view, which `Scene.setView()` walks the tree for once when it changes. A loop of `below` is reported once and broken. The editor measures the box it selects by the same sizes, so a layout and a selection never disagree.

A `CanvasLayer` marks a part of the scene that is drawn in screen space: what is under it ignores the scene's camera, is drawn after the world and its meshes, and gets input before the world does, which is how one scene holds both a level and its interface. Layers are ordered by their `layer`, a node's own priority only orders it inside its layer, and `visible` hides the whole layer and keeps input from it. A scene keeps the draw and input lists of each layer apart when the tree changes, so a frame still never walks the tree. The editor's scene view draws a layer through the camera, so the interface sits in the world where it can be picked and moved; the Game tab and a running game draw it in screen space.

`Button` is the one node the engine ships that takes input, which is why nodes have an `onEvent()` hook next to `update()` and `draw()`. The hook gets the event and nothing else: a node never holds a `Renderer` or a layer, and reads the size of its view from its scene. A scene receives the events of the layer it is in and hands each one to the nodes that have the hook, top first: the tree order reversed, then stable-sorted by priority, so the button drawn over another is the one pressed. The walk stops at the first node that sets `handled`. A button is held by the mouse or by one finger on the front touch device, shows as pressed while that pointer is over it, and calls `onClick` when the pointer is released over it; released elsewhere, it lets go without a click. Its state is `isPressed` and nothing more: no focus, so a gamepad cannot reach it yet. It hit tests through its scene's camera, so it works in world space as well as on an interface scene without one.

A `TouchButton` is a round button that holds an input action while a finger is on it, so a game reads it as it reads a key bound to that action. Its circle fills the shorter side of its control and is drawn with triangles, so it needs no texture on any platform. The left mouse button stands in for a finger, which is how it is tried on a computer. With `isPassBy` a finger that slides onto it presses it and one that slides off lets it go, and `platforms` says where it is drawn and pressed: platform keys such as `android web`, plus `auto` for wherever a finger touches the screen the game is drawn on (`Input.isTouchOnDisplay`). Empty means `auto`, which leaves out the DS and the 3DS, whose touch screen is another screen, and the calculator; a browser or a computer is named in the list when its mouse should get the control. The editor's scene view always draws it, so it can be placed, while a game the editor plays follows the list for the platform being previewed. `onPressed` and `onReleased` are there for what is not an action.

A `VirtualJoystick` is a stick on the screen that sets one vector2 action to where its tip is, from -1 to 1 on each axis with up negative, the way a gamepad's stick reads. It rests at the middle of its control, drawn as two circles, and the tip is held inside the base. Where Godot's `VirtualJoystick` presses four actions, this one sets a single vector2 action, so a game that moves with a stick, the keys and the D-pad reads one action for all of them. `deadzone` is the share of the base's radius the tip moves before anything is read, `isDynamic` moves the base to where a finger lands anywhere in the control, `isHiddenUntilTouched` draws it only while held, and `platforms` chooses where it shows, as for the `TouchButton`. The left mouse button stands in for a finger.
