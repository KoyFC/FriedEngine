# Nodes and draw order

A `fried.scene.Node` is a name, an id, an `active` flag and a list of child nodes. A scene is a tree of them under a hidden root, and what a thing is comes from its class: a game extends `Node` or one of the engine's typed nodes and overrides what it needs. The classes form a chain. `CanvasItem` adds a draw priority, visibility and a world position that everything drawn shares, and under it there are two branches: `Node2D`, placed by a position, rotation in degrees and scale relative to its parent (`Sprite`, `Camera` and `Collider` are `Node2D`s), and `Control`, placed against its parent's rectangle (`Label`, `TextureRect` and `Button`). `Node3D` is a third branch, placed by a position, a rotation in degrees about each axis and a scale on each, relative to the nearest `Node3D` above it; its rotation is applied about z, then x, then y, as Unity does, and a 2D node under it is placed as if it had no parent. A behavior that acts on another thing is a child node that acts on its `parent`, found with `findParent()`, which is what a scene file can hold and the editor can show. An earlier model gave every object a list of components and a transform component, with no hierarchy; the tree replaced it whole.

A drawn size belongs to the node that draws: a `Sprite` takes the texture's dimensions, or those of its source region, and multiplies them by the world scale, so no stored size can disagree with a scale.

`NodeBuilder` is a build macro that runs on every subclass of `Node`. For a class that declares `update()`, `draw()` or `onEvent()` it overrides `hookFlags()` to say so, and a scene keeps one list per hook, rebuilt by a single walk of the tree only when the tree changed: a node entered or left it, or a priority changed the order of events. A frame calls just the nodes that have the hook, so hundreds of plain nodes, such as the parents of a pool that are switched off, cost nothing per frame. The hooks are private and the calls are opened to the scene with a targeted `@:allow`, so a node overrides a hook and the frame calls it, but game code cannot call it by hand.

`activeInTree` and `shownInTree` cache what the ancestors allow. A change of `active` or `visible` rewrites them with one walk of that subtree, and the frame loops, `Physics` and the event walk read only the flags, never the chain of parents. A subtree stops with its parent: an inactive node switches off its children and their colliders with it.

A `Scene` updates every node and then draws every node, in two passes rather than one. All movement therefore happens before any drawing, so a node that another node moved in the same frame is never drawn where it used to be. With a single pass, tree order would quietly decide which nodes got a stale position. `update(delta)` receives the seconds the frame took, the value `Time.deltaSeconds` holds, so a movement takes its step from its own argument and not from a global.

The tree changes at once and the lists are refilled before the next pass, so a node can add or destroy others from inside `update()`; the loops skip a node that has left the scene. `destroy()` detaches a node, clears its scene and calls `destroyed()` on each node of its subtree, children first. `ready()` is called once per node, children before their parent, when it first enters a scene. A scene file builds its whole tree first, so every node and reference exists when `ready()` runs, and the editor player never readies them. A node made in code is readied as soon as it joins a scene, which is what spawning at run time relies on.

A `CanvasItem` caches its world position, rotation and scale. Setting a `Node2D` field, or moving an ancestor, marks it and the `CanvasItem`s below it dirty, and the next read works the value out again. A parent with no rotation and a scale of one, which is nearly every parent, takes additions only, since the DS has no FPU. Otherwise the local position is scaled and rotated by the parent's world values and added to its position.

A `Control` is placed against its parent's rectangle, with the vocabulary of Unity's interface: anchors as fractions of the rectangle, a pivot, an offset, and insets for an axis whose two anchors differ and the control is stretched between them. The parent's rectangle is a parent `Control`'s; a parent `Node2D` gives a point at its position, so a label under a node follows the node with its offsets as a position; under the root, or a plain `Node`, it is the view. A control's size is what its class says, such as a `Label`'s measured text or a `TextureRect`'s picture, scaled to fill a stretched axis, and otherwise its `width` and `height`. `below` stacks a control under another with the offset as the gap. Layout is part of reading the world position, so it happens again only after something it depends on changed: its own fields, its parent's rectangle, the control `below` names, a `Label`'s text or font, or the size of the scene's view, which `Scene.setView()` walks the tree for once when it changes. A loop of `below` is reported once and broken. The editor measures the box it selects by the same sizes, so a layout and a selection never disagree.

Drawing never reaches the renderer directly. A node's `draw()` submits a command to `fried.graphics.DrawQueue`, the loop flushes the queue between the update callback and `present()`, and the queue sorts before dispatching to the renderer. That is what separates the order things are drawn in from the order the code emits them in. Before the queue existed those two orders were the same thing, and changing what went on top meant moving lines.

The sort key is the triple of layer index, draw priority and submission index, ascending, so a smaller value is further back and equal ones keep the order they were submitted in. The submission index is unique within a frame, which makes the triple a total order: two commands never compare equal, so no sorting algorithm can produce a different picture from another. The guarantee is in the key rather than in the stability of an implementation.

Commands come from a pool that is reused between frames instead of one allocation per sprite per frame, since the cost that matters is GC pressure on a console. Each command copies the values it was given, including the contents of a `Rect` and the points and colors of a batch of triangles, so mutating a rect or an array after submitting cannot alter a command already queued. The pool grows to the largest frame the program has drawn and stops there.

The draw color is ambient renderer state that `clear()` also reads, so the queue takes note of it before dispatching and puts it back if any command changed it. Otherwise the last rectangle of one frame would become the background of the next. Flushing also happens when there is no renderer, minus the sorting and the dispatch, because a queue that only drained when something could draw would grow without a ceiling.

The queue is static, like `Time` and `Input`, and each command records the renderer it was submitted for. `DrawQueue.currentRenderTarget` names that renderer, `Scene.draw(renderer)` sets it for the length of a pass, and the loop points it at the first renderer before the update callback so a program with one window never has to know the field exists. A flush sorts once and then walks the commands once per renderer, so ordering is decided globally and dispatch is filtered per target. A frame's sprites, rectangles and outlines do not reach the renderer one call each: the walk writes them as records into two arrays, eight integers and five doubles to a record, and hands the whole run to the renderer in one `fried_renderer_draw_batch()`, which a command of another kind (text, triangles, a mesh) ends. The camera travels as a record of its own, and the numbers in a record are the world's: the placement through the camera, which the draw queue used to work out in Haxe, is done natively, and so is a sprite's size: a `Sprite` or a `TextureRect` queues its scale, in a record of its own kind, and the renderer multiplies it by the size of the texture or of its region. Every backend but the DS decodes the records back into the calls it had before, with the same arithmetic in the same order (`draw_batch.cpp`, which multiplies a scaled size as the sprite did), so what it draws is unchanged. The application flushes it but does not own a scene: framing a frame is the loop's job, while a scene is game content and nothing about a scene says there can only be one. A game drives its scenes through the layers of a renderer, or by hand from the update callback. One consequence is worth knowing: anything drawn by calling the renderer directly from that callback is drawn before the flush, so it ends up underneath everything queued, whatever priority the queued commands carry.

`Sprite` and the other nodes live in `fried.scene` rather than in `fried.graphics` so that the dependency runs one way. The scene knows what graphics are, and graphics know nothing about nodes, which is the same rule that keeps windows from knowing that renderers exist.

`Label` is the text node the engine ships, and it holds no texture. Each draw submits the string to the queue, and the renderer draws it a glyph at a time from an atlas: one texture per font and renderer, built on the first text drawn there, holding every glyph it has rasterized. Printable ASCII goes in when the atlas is built, and any other character is rasterized the first time it is drawn and stays. A string that changes every frame therefore costs layout and quads, never a texture. Rendering a whole string to a texture instead, which is what the engine did before the atlas, meant an SDL_ttf render, a format conversion, an allocation and an upload per change, all on the CPU, which on a 3DS is a 268 MHz ARM11.

The glyphs are rasterized in white and tinted when drawn, so one atlas serves every color, and the layout that places them is the one `Font.measureWidth()` measures with, so a box sized from it fits the line exactly. That layout is SDL_ttf's per glyph metrics plus kerning, which can differ by a pixel from what it would render for the whole string. Both are cached per font on the engine's side, so a frame makes no SDL_ttf call at all once its glyphs are in the atlas. That is not an optimization but a requirement: SDL_ttf caches 256 glyphs in slots picked by glyph index modulo 256, so asking it every frame about a line with two glyphs sharing a slot reloads both through FreeType, over and over. NunitoSans has eleven such pairs within ASCII, and asking for kerning per pair per frame took the sandbox from 60 FPS to 26 in Azahar. The atlas side grows with the line height, from 256 to 1024 pixels, the most the 3DS takes; a character that no longer fits is left out rather than failing the draw. Atlases go with their renderer, released by `fried_renderer_destroy()` before the renderer itself, and with their font. The font file itself is read into memory whole when it is loaded, because FreeType otherwise reads it a glyph at a time, and on a 2DS each of those reads goes through the romfs to the SD card: that alone kept the sandbox's first frame back 5.1 seconds from `main()`, against 0.6 with the file in memory.

An atlas is rasterized at the size its font covers on that renderer's screen, not at the size the text is laid out at. With a display scaled by 1.5, a 16 pixel font is rasterized at 24 and drawn back at 16 logical pixels, so the glyphs land one texel per output pixel instead of being enlarged or shrunk by the nearest filter, which had left text blocky when scaled up and unreadable when scaled down. When the scales of the two axes differ, as under `stretch`, the smaller one is used, since stretching a glyph costs less than dropping rows of it. The layout stays at the font's own size, so `measureWidth()` and `lineHeight` do not depend on the screen. The atlas opens its own copy of the font at that size from the file already in memory, and is rebuilt when the scale changes, such as when the window is resized. Where the display shrinks the game, as `height` does on a small screen, a font laid out at 16 pixels is rasterized at 6 and cannot be read, and the layout stays at the font's own size on purpose, so the world keeps its view. `Renderer.pixelScale` says how many output pixels a logical one covers, and `Renderer.legibleSize(size, screenPixels)` gives the logical size that is at least that tall on the output, which the game asks for when it creates its font. A font in a scene file asks the same with an optional `minScreenSize` beside its `size`.

`textWidth` and `textHeight` come from the font and are measured once per change of `text`, `font` or `maxWidth`, so a size is there before the first frame: the sandbox sizes its hint panel around a label that has never been drawn. One `Label` is one line unless it has a `maxWidth`: then it is broken between words into lines no wider than that, and a word wider than it gets a line of its own. Its size is that of the whole block, and the editor shows the same block. Each line is submitted on its own, so a broken text is not meant to be rotated.

`Button` is the one node the engine ships that takes input, which is why nodes have an `onEvent()` hook next to `update()` and `draw()`. The hook gets the event and nothing else: a node never holds a `Renderer` or a layer, and reads the size of its view from its scene. A scene receives the events of the layer it is in and hands each one to the nodes that have the hook, top first: the tree order reversed, then stable-sorted by priority, so the button drawn over another is the one pressed. The walk stops at the first node that sets `handled`. A button is held by the mouse or by one finger on the front touch device, shows as pressed while that pointer is over it, and calls `onClick` when the pointer is released over it; released elsewhere, it lets go without a click. Its state is `isPressed` and nothing more: no focus, so a gamepad cannot reach it yet. It hit tests through its scene's camera, so it works in world space as well as on an interface scene without one.

A draw priority is a single flat number within its layer, not inherited from a parent, and a game sets it on the node at any time, including from a node in the middle of a frame.
