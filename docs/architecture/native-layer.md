# SDL2 and the native layer

SDL2 and its three companion libraries (SDL2_image, SDL2_mixer, SDL2_ttf) are initialized together in `native/platform/application.cpp`, so failing to bring one up fails `fried.Application.init()` rather than surfacing later at the first load.

On a console they are found as packages from its SDK. On PC, `cmake/PcDependencies.cmake` downloads pinned release tarballs and builds all four from source, so building for PC needs nothing installed beyond Haxe, CMake and a compiler, and every machine builds against the same versions. That matters more than it looks: on a distribution that ships SDL2 as sdl2-compat, as Fedora does, the installed "SDL2" is SDL3 underneath and does not behave like SDL2. `FRIED_SYSTEM_SDL2` links the installed packages instead. Building from source is all or nothing, because an installed SDL2 next to a companion library built from source would define the same targets twice.

All four are linked statically, so the executable needs no SDL2 library next to it, and each is built with only the formats the engine loads. SDL2_image reads PNG and JPEG through stb_image and SDL2_mixer reads WAV, OGG and MP3 through decoders it carries, so neither needs a library under it. That leaves FreeType as the only one, and it comes inside SDL2_ttf's own release tarball, which is why the tarballs are fetched rather than the repositories, where it is a submodule.

The sources are unpacked once per machine into `FRIED_DEPS_CACHE`, one folder per release, such as `SDL2-2.32.10`, and the four libraries are compiled once per machine too, installed into `FRIED_DEPS_CACHE/installed/<system>-<hash>`. The compilation is a CMake build of its own (`cmake/pc_sdl2/`), run with `execute_process` during the first configure that needs it and given the same generator, toolchain file, compiler and flags as the build tree, with both Debug and Release for a multi-config generator. A game's build tree then only runs `find_package` on the installed package configs, which is why a second build tree configures in about a second.

The hash covers everything that changes the result: the system and processor, the compiler's identity and version, the compiler flags, the MSVC runtime, the generator's platform and toolset, the build type for a single-config generator, and the contents of `cmake/pc_sdl2/CMakeLists.txt`, so changing a version or an option there installs into a new folder rather than reusing a stale one. An install is reused only once it holds the `.fried-installed` marker written after it completed, and a lock file beside it keeps two configures from building the same one at once. The sources follow the same rule with their `.fried-unpacked` marker: a folder without it, left by a download that was interrupted, is unpacked again.

Nothing in a build tree is compiled from the sources, so build trees for different systems and configurations share them safely. The installed headers are copied into `_deps/sdl2-companion-headers` in the build tree, so an editor finds all of them at a fixed path whichever cache they were installed in. On Linux, SDL2 still loads X11, Wayland and the audio server at run time, so building it needs their development headers, and a backend whose headers are missing is left out of the build.

Under XWayland, an X11 window in a Wayland session, a renderer asked for vsync is created without it, reports `isVsyncEnabled` as false, and the loop paces frames to `Application.targetFps` instead. A vsynced present there stalled while the cursor moved over the window, taking 60 FPS down to around 41 while the game spent under a millisecond per frame, and the compositor already syncs what it shows to the display, so nothing tears without it. SDL's Wayland driver had no stall either, but Wayland never lets a client read or set its window's position, and the engine keeps `Window.setPosition()`. The cost is that the rate is the target rather than the display's: a 144 Hz screen gets 60 unless the game raises `targetFps`.

A window on PC is created hidden and shown by `fried_renderer_create()`, because SDL2's OpenGL renderers recreate the window they are given, and a window shown before that flashes on screen before its replacement appears.

`native/` is hand-written C++ glue wrapping only the SDL2 calls the engine actually makes, bound to Haxe through a small `extern class` per file. The one exception is drawing on the 3DS, which goes through citro2d instead (see [Nintendo 3DS](../platforms/3ds.md)). No SDL pointer type crosses into Haxe: windows, renderers and textures are tracked by integer handle (`native/handle_pool.h`). Game code never sees SDL2, only the `fried.*` types.

`native/scene/` is not SDL glue but data that components keep in C++: today the transforms of `Transform2D`s, one slot for each in a scene. The Haxe output is the same for every target, so a platform that needs another representation has its own implementation of the same header chosen by CMake: the DS keeps a slot in fixed point (`transform2d_nds.cpp`), since it has no floating point unit and every `Float` operation there is a call into software, and the others keep floats (`transform2d.cpp`), as every number that crosses into this layer is a `float`.

`native/physics/` holds the same kind of thing for colliders: `collider_store.cpp` keeps the boxes of a scene's colliders in one array, with the grid that finds the ones near a box, and answers the overlap queries. It is plain integer code, the same on every platform, since a box is already in 20.12 by the time it gets there.

Numbers that cross from Haxe in an array, such as the points of a triangle or the placement of a mesh, are `fried_real` (`native/math/real.h`), which is whatever Haxe's `Float` is in that build: a `double`, or a `float` when the platform's `precision` in `project.fried` is `"single"`, as it is for the DS unless the project says otherwise (CMake's `FRIED_FLOAT32`, set by `cmake/ProjectPrecision.cmake`). A native function that takes a `Float` by value needs nothing, since C++ converts it, but one that takes a pointer to them has to agree with Haxe on its type. `native/platform/clock.cpp` is the clock `Time` reads, whole microseconds in an `int` that wraps and a difference taken across the wrap, with a version for the DS that reads the tick counter.

A failure that reaches Haxe as a thrown error carries SDL's own explanation with it. Every failing path in `native/` calls `fried_capture_sdl_error()` or `fried_set_last_error()` before it returns, and `fried.NativeError.describe()` appends what it stored, so `Failed to load texture: x.png` becomes `Failed to load texture: x.png (Unsupported image format)`. Missing file and wrong format are otherwise the same message.

The error is copied at the point of failure rather than read later, because the next SDL call overwrites it. `fried_application_init()` is where that is not theoretical: each of its failure paths tears down the libraries it already brought up, and every one of those teardown calls would replace the error that explains why it is tearing down.

Two things reach Haxe as events rather than as state because SDL only reports them that way: the mouse wheel, accumulated per frame in `native/platform/mouse.cpp`, and gamepad connection, handled in `native/platform/gamepad.cpp`. Window events are translated into a small queue that Haxe drains after SDL polling is over, so a game callback never runs while SDL state is mid-update. `native/platform/events.cpp` keeps a second queue of the same shape for input events, so keyboard, mouse, gamepad and touch activity crosses as a stream as well as as state. One pass over SDL's events fills both, and `fried.Events` drains the window half while `fried.input.Input` drains the input half, so each Haxe type owns the events it exposes rather than one type owning the header.
