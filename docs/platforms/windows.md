# Windows

Building is covered in [Building](../getting-started/building.md#windows-from-linux) from Linux and in [Building](../getting-started/building.md#windows-on-windows) on Windows.

## How the port works

Windows is built with MSVC on Windows, where CMake finds Visual Studio on its own, and with MinGW-w64 either on Windows or from Linux. A build from Linux is configured with `cmake/toolchains/mingw-w64.cmake`, the one toolchain file the engine ships itself, since no SDK brings one. `native/` needed no change for any of them: SDL2 is built from source for Windows as it is for Linux, and `SDL_GetBasePath()` and `SDL_GetPrefPath()` answer the executable's folder and `AppData\Roaming`.

Under MSVC, hxcpp's runtime compiles with `/bigobj`, which its own build passes for Debug, in place of the GCC flags every other platform takes. `haxelib` answers with Windows line endings and backslashes there, so `cmake/Hxcpp.cmake` strips the one and converts the other before using the path.

MinGW-w64 needed three things in `cmake/Hxcpp.cmake` that hxcpp's own build tool never runs into, because it builds Windows with MSVC on Windows. Its `Dynamic(long)` overloads are keyed off `__WORDSIZE`, which only glibc defines, so MinGW-w64 gets `__WORDSIZE=32`, the size of a Windows `long`; without them a `DWORD` converts ambiguously. `Socket.cpp` includes `Ws2tcpip.h` as the Windows SDK spells it, which a case-sensitive host cannot find among MinGW-w64's lower case headers, so `cmake/mingw/` holds a header of that name forwarding to the real one. The same file also warns twice over under GCC: it defines `_WIN32_WINNT` as `0x0501` after MinGW-w64's headers have already set a newer one, so that file alone is compiled with `0x0501` given up front, which keeps MinGW-w64 from setting its own and makes hxcpp's definition a harmless repeat; and it puts `dllimport` on two function pointer typedefs, where GCC ignores it, so `-Wno-attributes` is passed for that file only. And both compilers link `ws2_32`, which `Build.xml` names and the source list in `cmake/Hxcpp.cmake` does not carry.

Either way the executable needs nothing beyond what Windows ships. MinGW-w64 links with `-static`, so it carries libstdc++, libgcc and winpthread instead of depending on MinGW-w64's DLLs, and MSVC links its C++ runtime statically, which every library in the executable has to agree on, so `cmake/FriedEngine.cmake` sets it before SDL2 is built. Every configuration but Debug is linked for the GUI subsystem, which keeps Windows from opening a console window next to the game. MSVC enters that subsystem through `WinMain()` by default, and hxcpp declares `main()`, so its entry point is set back to the console one.
