# Casio fx-CG50

## Requirements

- The [fxSDK](https://git.planet-casio.com/Lephenixnoir/fxsdk) with gint, its `sh-elf-gcc` and its libstdc++.
- That libstdc++ rebuilt with exceptions by [`packaging/cg50/`](https://github.com/KoyFC/FriedEngine/tree/main/packaging/cg50), since the fxSDK builds it without them.
- No SDL2 is involved: gint is the whole platform there.

## Building

The fxSDK's toolchain file sits under its install prefix (`~/.local` by default):

```sh
cmake -S . -B build/cg50 -DCMAKE_TOOLCHAIN_FILE=$HOME/.local/lib/cmake/fxsdk/FXCG50.cmake
cmake --build build/cg50
```

### Output

That produces `build/cg50/sandbox/fried_sandbox.g3a` and, next to it, a `Fried Sandbox/` folder holding the assets. The assets stay outside the `.g3a`, which holds at most 2 MB, and audio is left out of them, since the calculator cannot play it, which configuring a project that lists `cg50` in `platforms` warns about, counting the files; the game still loads and plays its sounds, silently.

### Running

- With the calculator connected over USB in its storage mode, both go at the root of its storage memory, and the add-in then appears in the main menu.
- MENU always leaves for the calculator's main menu, as it does in every add-in, and the game sees its window lose and regain focus around it.

### Notes

- The screen is 396x224 and the keypad is the keyboard: the digits, the arrows, EXE as Enter, EXIT as Escape, DEL as Backspace, F1 to F6, SHIFT and ALPHA are those keys, the twelve keys above the digits are the letters A to L that ALPHA types with them, and the point key is Space.
- Text set in a font too large for the calculator's memory, as the sandbox's is, falls back to the calculator's own pixel font.
- Everything is drawn by the CPU, so the sandbox runs at around 43 frames a second with neither of its overlays, 25 with one of them and 19 with both, and writing user data pauses the game for a moment, since the calculator's storage is slow to write.

## How the port works

An fx-CG50 build is configured with the fxSDK's toolchain file. That toolchain names its platform in `FXSDK_PLATFORM_LONG` rather than setting a flag of the kind the consoles' toolchains set, so `cmake/FriedEngine.cmake` turns it into `FRIED_CG50` for CMake, and the C++ keys off the toolchain's own `TARGET_FXCG50`. `cmake/CG50.cmake` finds gint, packages the `.g3a` and holds everything below that is the calculator's alone.

It is the one platform with no SDL2 at all. The calculator runs [gint](https://git.planet-casio.com/Lephenixnoir/gint), a small kernel that takes the hardware over from the OS, and there is no SDL2 port to it, so every file in `native/` that calls SDL has a sibling, chosen by `cmake/FriedEngine.cmake` the way the 3DS chooses its citro2d renderer. Most are `_gint` files; the renderer, the textures and the fonts are `renderer_software.cpp`, `texture_software.cpp` and `font_software.cpp`, which draw with the CPU into a frame the platform hands them through `graphics/software_frame.h`, and fall back to a pixel font it carries through `graphics/pixel_font.h`. `software_frame_gint.cpp` and `pixel_font_gint.cpp` are the calculator's side of those two.

A font keeps the last 64 lines it drew, each with its layout and its glyphs' places in the atlas, so a line drawn again as it was, which is most of a game's text, is not laid out again. The renderer does not draw a call as it comes: it records it as a command in output pixels, with the bounds it covers, and draws the frame at present. The frame still holds what the last one's commands drew, so the two lists are compared, a command at a time, and only where they differ is drawn again, every command clipped to it, and sent to the screen; a quad is worked out to fixed point once, as it is recorded, so drawing it again costs no float operation. A texture loaded, destroyed or written to, a change of display layout, or the screen lost to the main menu has all of it drawn again.

The window is the 396x224 screen. Keys come from gint's keyboard driver as SDL scancodes, so `fried.input.Key` needed no change: the digits, the arrows, EXE, EXIT, DEL, F1 to F6, SHIFT and ALPHA are the keys a keyboard has, and the twelve keys above the digits are the letters ALPHA types with them. MENU is left to the calculator, as every add-in leaves it, and reaches the game as its window losing and regaining focus. There is no mouse, touchscreen or gamepad, so those report nothing, and no audio output, so sounds and music load and play without ever being read: the build leaves audio out of the assets it stages.

Drawing is done by the CPU into gint's RGB565 frame, through the same display layout the GPU backends take. Only reaching the frame, keeping the cache in step with it and sending it to the screen belong to gint, and the pixel format is the frame header's, so the rasterizer itself knows nothing about the calculator.

The SH4 has no floating point unit, so a quad is mapped back to its texels in 16.16 fixed point, unturned quads skip the trigonometry, and a translucent pixel is blended with one multiplication by a 5-bit alpha over the color's three fields spread apart in 32 bits, which made a large translucent rectangle four times cheaper than blending each channel on its own. A row of a translucent rectangle is blended two pixels per memory access. A triangle is filled a row at a time between its edges, stepped in the same fixed point, and covers the pixels whose centers fall inside it, so two triangles sharing an edge never draw a pixel on it twice.

gint places its frame in uncached memory, so the renderer reaches it through the cache instead, writing every line back before the DMA sends the frame to the display and discarding it before the DMA clears the frame, which halved the cost of an overlay covering the screen.

Text drawn unturned at its own size skips the quad mapping and copies each glyph from the atlas a whole pixel at a time, because setting a quad up in software floating point cost several times what drawing the glyph did. That holds under any display scale: the line's glyphs are laid out again at the size the atlas was rasterized at, so each lands one texel per output pixel, and a fixed-height world on the calculator costs no more per line of text than a native one. A second frame, so that sending one to the display could overlap drawing the next, was tried and made the frame slower overall, since the DMA then competes with the CPU for the bus.

PNGs are decoded by stb_image, the decoder SDL2_image uses inside, and stored in the screen's own format with an alpha channel only where an image has one. Text is rasterized by stb_truetype into the same glyph atlas, laid out as `font.cpp` lays it out, but stb_truetype reads a font in place, and a font too large for the calculator's memory, such as the 569 KB one the engine ships, falls back to gint's own pixel font at a whole multiple of its size,, rounded for the size the atlas is rasterized at, so the glyphs stay sharp at any display scale.

A game is its `.g3a` and a folder of the same name at the root of the calculator's storage, holding `assets/` and the user data in `data/`. The `.g3a` holds at most 2 MB, which is why the assets stay outside it, and also why every configuration is compiled with `-Os`: unoptimized, the engine alone outgrows it, and `-O3` makes it over a quarter larger.

Files are where the calculator is least forgiving. gint reaches the storage through the OS, which must not run while gint has the hardware, so every file call has to go back to the OS through a world switch; one write made without it reset a calculator to its first-start setup. gint and the C library are built with LTO, which the linker's `--wrap` does not see into, so `cmake/gint/os_filesystem.cpp` defines gint's file functions itself, the same ones with the switch around them, and the linker takes those instead. Every switch costs time, which is why a file is read in one call and why writing user data pauses a game.

hxcpp needed more here than on any console, all of it in `cmake/gint/` and in copies of four of its sources that `cmake/CG50.cmake` patches into the build tree, failing at configure time if a new hxcpp moves the lines it patches.

fxlibc is far from POSIX, so `cmake/gint/` provides the headers it lacks, single-threaded stand-ins for pthreads and semaphores among them, and `runtime.cpp` answers the rest.

Immix reserves its blocks a megabyte at a time, more than any gint heap holds, and starts helper threads even in a single-threaded build, which gint cannot run, so the copy reserves 128 KB at a time and keeps one thread. Thread information goes in a `thread_local`, which the SH4 reaches through a register gint never sets up, so the copy keeps it in hxcpp's single-threaded form.

The SH4 faults on a misaligned read, which a string's hash, kept right after its last character, usually is, so the copies read and write it a byte at a time, and `HXCPP_ALIGN_ALLOC` aligns everything else. The garbage collector would ask for 8 MB of working memory, ten times the calculator's, so `runtime.cpp` answers its environment variables with sizes that fit. `Sys.time()` reads a millisecond timer instead of fxlibc's clock, which only ticks 128 times a second.

A Haxe `throw` is a C++ `throw`, and three things stood between gint and one that lands in its `catch`: the fxSDK's libstdc++ is built without exceptions, so `__cxa_throw` has no unwind tables, which `packaging/cg50/` fixes by rebuilding it; gint's linker script discards the unwind tables of everything else, so `cmake/CG50.cmake` writes a copy of it that keeps them; and gint links no `crtbegin.o`, which would have registered them with the unwinder, so `runtime.cpp` does.
