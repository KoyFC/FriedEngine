# Nintendo DS

## Requirements

- devkitPro, installed as described in [Installing](../getting-started/installing.md#devkitpro), with `dkp-pacman -S nds-dev`.
- No SDL2 is involved: libnds is the whole platform there.

## Building

```sh
cmake -S . -B build/nds -DCMAKE_TOOLCHAIN_FILE=$DEVKITPRO/cmake/NDS.cmake -DCMAKE_BUILD_TYPE=Release
cmake --build build/nds
```

### Output

That produces `build/nds/sandbox/fried_sandbox.nds`, with its assets inside it in NitroFS, which runs from a flashcart or in melonDS.

### Running

- User data goes to `/data/<name>/` on a FAT volume, the flashcart's or the DSi's SD card, and the program stops without one: in melonDS, enable DLDI under Config, Emu settings, DLDI, with an SD card image, such as one made by `mkfs.fat -C -F 32 dldi.img 131072`.

### Notes

- `Release` (`-O2`) is the build to use on the DS: its draw calls took 20 % less time in melonDS than with the native code at `-Oz`, for about 27 KB more code. Why `MinSizeRel` is safe is explained in [The build type and strings](#the-build-type-and-strings).
- The scene draws on the top screen at 256x192 and the debug overlay moves to the bottom one, as on the 3DS; once the program ends, the bottom screen shows the end of the log, where an error that stopped it stays until a button is pressed.
- The top screen is drawn by the DS's 3D engine and the bottom one, when the game opens a second window there, on the CPU: the sandbox runs at 60 frames a second in melonDS with its debug overlay on the second.

## How the port works

A DS build is configured with devkitPro's DS toolchain file, which sets `NINTENDO_DS` and defines `__NDS__`, and brings `nds_create_rom()` the way the 3DS's brings `ctr_create_3dsx()`. There is no SDL2 for it, so like the calculator it has a sibling for every file in `native/` that calls SDL, chosen by `cmake/FriedEngine.cmake`: `_nds` files for the application, the events, the filesystem, the gamepad, the touchscreen, the window and the sounds, and the calculator's own files for the keyboard, the mouse and the music, which hold state no DS code reports to. Each screen is a window at 256x192, as on the 3DS, the top one opened first.

The DS's buttons are the one gamepad, always connected, read once a frame by `gamepad_nds.cpp` when the events are pumped. They are placed by position, as `fried.input.GamepadButton` names them, so A is east and B south, and A accepts, as on the 3DS and the Switch. There is no stick and there are no triggers, so the axes read zero and L2 and R2 never go down; the sandbox moves its player with the d-pad as well as the stick for that. The touchscreen is one device with one finger, read by `touch_nds.cpp` in the same pump, and belongs to the bottom screen's window as it does on the 3DS, with its position in that window's logical pixels; with no window there, a touch is no one's and is not reported.

The top screen is drawn by the DS's 3D engine, through libnds's videoGL, by `renderer_nds.cpp` and `texture_nds.cpp`; the CPU renderer the calculator uses ran the sandbox at 12 frames a second here, held back by how slowly main RAM takes writes. Quads and triangles go out in screen pixels under an orthographic projection with one vertex unit a pixel. The engine draws opaque polygons before translucent ones, so each polygon is given a depth one step nearer than the last, which keeps the order they were drawn in across the two, and translucent ones go in the order they came (`GL_TRANS_MANUALSORT`) with a polygon ID of their own each, since translucent pixels do not blend over those of the same ID. A polygon alpha of zero means a wireframe to the engine, so nothing that faint is drawn. `glFlush()` swaps at the next vertical blank and the engine takes no new polygons until then, so a renderer reports vsync. The vertices are computed in integers wherever they can be, as every float operation is a call into the software floating point library: a line of glyphs sent through floats took ten times as long. A logical edge becomes an output pixel in one step, its position times the scale, skipped at a scale of one, rounded half away from zero from the float's bits by `toVertexUnits()` in `renderer_nds.cpp`, with no float comparison, and a quad's last three vertices go as one write each (`VTX_XY`), since they share the first one's depth. A line of text that is not turned or resized is blitted glyph by glyph at any display scale, as the calculator does: the atlas is rasterized at the size the text covers on the screen, so only the line's origin goes through the scale and every glyph's offset and size is already in output pixels. A quad with no texture sends no texel coordinates either, as the engine ignores them. A batch is decoded in integers: a double's bits become 16.16 fixed point, the camera and the display's scale are applied in it, and a rotated sprite turns about its middle with libnds's sine table, so none of it calls into software floating point. Quads that are opaque and share a texture, or have none, share one polygon format, texture binding and list, so a run of sprites or of boxes is set up once; a translucent one keeps a polygon ID of its own and never shares.

Meshes are turned, lit and depth tested by the engine itself, which the CPU path took about 2 ms a cube for. `mesh_nds.cpp` packs a mesh once, when it is created, into the command words the engine's FIFO takes: a normal and the corners in fixed point for each polygon, and the material where the color changes, in a list for each run of one alpha and one corner count. It joins two triangles in a row that make a flat, convex quad of one color into that quad, since the engine keeps at most 6144 vertices a frame and a quad takes four where two triangles take six. `renderer_nds.cpp` draws meshes under a projection of its own, built from the camera's numbers, that puts them in perspective on the screen the 2D draws are on, with their depth in a band of 1024 steps past the last 2D polygon's, so they keep their place in the draw order, and meshes drawn one after another with the same view share a band and are depth tested against each other in it. The band is reached only infinitely far away, so there is no far plane, but a mesh more than 4096 units from the camera is not drawn, as its position would overflow the projection's fixed point. The light's ambient share of a polygon's color goes in as emission and the rest as the light's color, which is how `Camera3D` shades. Each mesh then costs a few matrix commands and a DMA of each of its lists, all in integers: placement numbers are turned to fixed point from the bits of the double, as each call into software floating point costs about as much as a mesh's matrices. Sending a list by DMA took the polygon loop, which was most of a mesh's cost in the emulator, down to the time the geometry engine needs to take it (see [the measurements](../development/ds-3d-measurements.md)). `sendCommands()` waits until channel 0 has handed the words to the FIFO, since a direct write is not ordered against a DMA still in flight, and the polygon's alpha and its rotating translucent ID stay outside the lists, which `startPolygons()` sets first. The emission in a list is the light's ambient share of its color, so `fried_mesh_set_ambient_nds()` writes it again, and flushes the words from the data cache, when a mesh is drawn under another ambient. Projecting turns y over, so a polygon that faces the camera goes round the other way to the engine, and meshes cull its front faces. Past the engine's 2048 polygons or 6144 vertices a frame, whatever comes last is not drawn: 512 of the sandbox's cubes fill the vertices.

Textures sit in VRAM banks A and B at power of two sizes up to 1024 texels a side, with an image in the top left corner of the one that holds it and one larger halved until it fits, which configuring a project that lists `nds` in `platforms` warns about for each PNG over the limit. An image's texels are 15-bit color with one bit of alpha, drawn where it is at least half opaque. Fonts are rasterized on the CPU by the calculator's `font_software.cpp`, into a blank texture that holds five bits of coverage over a white palette; it keeps a copy of its texels in main RAM, since VRAM takes no byte writes, and what a frame changes is copied across in the vertical blank after it, since the 3D engine reads textures all the while the screen is drawn. Those two banks are 256 KB for every texture a game has, so an atlas is sized from its own printable ASCII, packed as it will be packed, with a third of its height again spare for other characters, rather than as a square from the line height: that square was 512x512 for an 18 pixel font, the whole of both banks, and left no room for the game's images. The fx-CG50 shares the sizing, and the memory it saves. The DS carries no pixel font the engine draws with, so a TrueType font that does not fit in memory fails to load, and the sandbox's 569 KB one fits.

The project's `display` applies to the top screen only, as on the 3DS: the bottom screen is drawn by the software renderer at its own 256x192, as the 3DS draws its bottom one. The 3D engine shows on one screen at a time, so the bottom screen, when a game opens a window there, is drawn by the calculator's software renderer and textures, into a frame `software_frame_nds.cpp` copies to a 16-bit bitmap background of the sub 2D engine at each vertical blank. Its pixels are BGR555 with the top bit set where one is shown, so `graphics/software_frame.h` gives the renderer that format and a bit it sets on every color it writes, which is zero on the calculator. Both renderers are linked into one program: `renderer_software.cpp` and `texture_software.cpp` are compiled with `graphics/software_names_nds.h` forced in ahead of everything, which renames their entry points, so the calculator's files stay as they are, and `renderer_nds.cpp` and `texture_nds.cpp` hand the bottom screen's calls to them. Each side numbers its renderers and textures from zero, so the software side's public ids start at `FRIED_SOFTWARE_ID_BASE`, and a texture of one side drawn by the other draws nothing, as one that is not loaded does. The sandbox puts its debug overlay on the bottom window, and since only the lines of it that change are drawn again each frame, it runs at 60 frames a second with it there.

hxcpp needed three things, two of them already known. The ARM946E-S is ARMv5TE, which has no exclusive loads and stores, so every atomic the garbage collector uses is a call devkitARM has no library to answer, and `cmake/nds/runtime.cpp` answers it with interrupts masked. calico's `gettimeofday()` has only the RTC's whole seconds, which `Sys.time()` reads, so `runtime.cpp` replaces it with calico's system tick counter, anchored to the RTC. `Clock` reads the same counter directly, through `fried_nds_tick_count()`, which `runtime.cpp` starts once for both. And newlib's pthread keys are stubs that fail here, which is the 3DS's failure exactly, so the DS takes the same `thread_local` header through `HX_TLS_H_OVERRIDE`. Built as Thumb, the collector frees objects that are still reachable, so the runtime is ARM. The Haxe code the project generates is the part that is big, and `cmake/Hxcpp.cmake` builds that as Thumb, which takes a fifth off the program (2.58 MB to 2.01 MB for the sandbox) and leaves that much to the heap: without it the sandbox's 3D scene does not fit the 4 MB. It ran for thousands of frames and several scene changes in melonDS without the collector freeing anything it should not have, but it has not been tried on hardware, and `-DFRIED_DS_THUMB=OFF` builds it as ARM. hxcpp reads the flags word in front of each string literal as an int, and `-Oz` stops GCC aligning string literals to a word, so on the ARM9 an unaligned load came back rotated and strings were taken for the wrong encoding (`Json.parse()` failed on any number): `cmake/Hxcpp.cmake` builds the hxcpp code of a `MinSizeRel` DS build at `-O2`. The collector reserves its blocks 4 at a time instead of 32, from a copy of hxcpp's `Immix.cpp` that `fried_nds_patch_hxcpp()` in `cmake/NDS.cmake` writes into the build tree, as the fx-CG50 does: 142 KB less heap in use on the sandbox with 450 draw commands a frame. The heap ends at 0x023f0000, which `getHeapLimit()` reports, so a game with its font and HUD loaded can have under 100 KB of it left. When hxcpp cannot get memory for a large object it prints "Memory Exhausted!" and executes `__builtin_trap()` (`DebuggerTrap()` in its `Immix.cpp`), which is a CPU exception and not a Haxe error, so nothing catches it; it shows as the exception screen, and the message is lost when a window owns the bottom screen.

The program leaves about 1.8 MB of the 4 MB of RAM to the heap, which the garbage collector, every node and every font file share. The import therefore leaves unused tables out of each TrueType font (see Import settings): the engine's font would otherwise be 569 KB of it. A game that runs out of it, or ends on an exception nothing caught, stops with the reason and the last lines of the log on the bottom screen and waits for a button before the DS turns off, as the text console does for any other error.

Haxe's `Float` is a 32-bit `float` on this platform, which hxcpp calls `HXCPP_FLOAT32` and `project.fried` calls the `precision` of the platform's section: `"single"` is the default here, and `"nds": {"precision": "double"}` turns it off. The ARM9 has no floating point unit, so every `double` operation is a call into software, and a `float` one is about a third cheaper; with every `Float` of a game a `float` there is no operation left that has to widen to a double and back, which costs more than either. The sandbox's physics benches ran 6 to 10% faster in melonDS with it and the integer clock, and the scene benches 1 to 2%. What it costs is precision: a `Float` holds 24 bits, so an `Int` above 16,777,216 held in a `Float` is rounded, and a number parsed from JSON is a `float` too. `Sys.time()` reads seconds since 1970 as a `Float` and cannot be used for a duration here, which is why the engine reads `Clock` instead. Every platform but the calculator builds with it when its section asks (`"precision": "single"`), and the 3DS would gain less, since its CPU has a floating point unit that does a `float` faster than a `double` but not three times faster; it has not been measured on hardware.

The assets are staged into NitroFS by the same `cmake/DevkitProRomfs.cmake` the 3DS and the Switch use, under `nitro:/assets/`. User data needs a FAT volume, the DSi's SD card or a flashcart's through its DLDI driver, and goes to `/data/<name>/` on it, the flat list of one directory per homebrew program that DS homebrew keeps; with neither, `fried.io.UserData` throws as it does wherever no writable path resolves. The bottom screen is libnds's text console otherwise, which standard output and standard error print to, so the log is read there. `console_nds.cpp` keeps the last kilobyte printed whatever has the screen, and while a window does, nothing is shown; when the window closes, or the program ends, the console takes the screen back and prints what was kept. Returning from `main()` powers the console off, so the DS waits for a button first, which is what leaves an error nothing caught on the screen long enough to read. A sound is a PCM WAV read whole into main RAM, mixed down to mono and to signed samples, and played by the sound hardware from there at the file's own rate on one of channels 0 to 14, which mix it themselves, so a sound playing costs the ARM9 nothing; when all fifteen are busy, the one started longest ago gives way. The ARM9 reaches the channels only through the ARM7, which reports what is playing when it gets round to it, so whether a sound is still playing is worked out from when it started and how long it lasts, and one played a set number of times loops in the hardware until the frame it is due to end. A track is a WAV too, but one too large for RAM, so it is read from NitroFS a little ahead of where it plays: channel 15 loops over a ring of 32768 samples, and every frame the ring is refilled behind the point the channel has reached, worked out from the clock and the rate its timer really runs at, which is the sound clock divided by the timer rather than the file's rate. The channel starts on the frame after the track is played, because a game often plays its music just before a first frame that takes longer than the ring lasts; a pause stops the channel, and the ring is turned on resume so the sample it stopped on is where the channel starts again. A frame that stalls for longer than the ring lasts, about 0.74 seconds at 44.1 kHz, makes the channel play the ring around again before the music carries on.

### The build type and strings

`MinSizeRel` is safe on the DS only because `cmake/Hxcpp.cmake` builds the hxcpp code at `-O2` regardless: at `-Oz` GCC stops aligning string literals, hxcpp reads a header word in front of each one, and the ARM9 turns the unaligned load into garbage, so strings are taken for the wrong encoding and scene files fail to parse with `The scene file is version 0`. If that error ever appears on a DS build, check the optimization level of the hxcpp sources first.
