# Fried Engine Architecture

This document describes the **currently implemented** architecture of this repository. See `README.md` for the roadmap of what's coming.

## Scope of this repository

This repository is Fried Engine itself. Fried Build, Fried CLI and Fried Project Manager are separate tools, not yet built, that will live in their own repositories and consume this one as a dependency (a game project will pull this repo in as a pinned Git submodule). None of them exist yet.

## Build pipeline (implemented)

```
Haxe  --(hxcpp)-->  generated C++  --(CMake)-->  compiler  -->  executable
```

A minimal sandbox Haxe program is compiled to C++ by hxcpp (`haxe build.hxml`, using `-D no-compilation` to stop before hxcpp's own build tool would run), and that generated C++ is then compiled and linked purely by CMake. `cmake/Hxcpp.cmake` locates the `hxcpp` haxelib and compiles its runtime sources alongside the generated code, with no dependency on hxcpp's own `Build.xml`/`haxelib run hxcpp` build tool.

CMake is the build system for every platform this engine targets. Two are implemented: PC (verified on Linux/GCC) and PlayStation Vita (verified on real hardware), the second one described below.

## SDL2 (implemented)

SDL2 is linked via CMake's own package config (`find_package(SDL2 CONFIG)`, `SDL2::SDL2`), together with its three companion libraries, SDL2_image, SDL2_mixer and SDL2_ttf, each found and linked the same way. They are initialized and torn down alongside SDL itself in `platform/application.cpp` (`IMG_Init` for PNG, `TTF_Init`, `Mix_OpenAudio` at 44100Hz stereo), so that a failure to bring one up fails `fried.Application.init()` rather than surfacing later, at the first load. Each of the three is what one resource type loads through: SDL_image for `fried.graphics.Texture`, SDL_ttf for `fried.graphics.Font`, SDL_mixer for `fried.audio.Sound` and `fried.audio.Music`. `native/` holds small, hand-written C glue files that wrap the specific SDL2 calls the engine needs (`platform/application.cpp`: `SDL_Init`/`SDL_Quit`; `platform/events.cpp`: polling for `SDL_QUIT`, also forwarding `SDL_MOUSEWHEEL` events to `platform/mouse.cpp` since SDL2 only reports the wheel through events, not a poll-able state, forwarding `SDL_CONTROLLERDEVICE*` events to `platform/gamepad.cpp` for the same reason, and translating `SDL_WINDOWEVENT` into a small queue of window events that Haxe drains once SDL polling is over; `platform/window.cpp`: creating/destroying an `SDL_Window`, tracked by integer handle so no SDL pointer types cross into Haxe, and resolving SDL's own window id back to that handle for `platform/events.cpp`; `graphics/renderer.cpp`: creating an `SDL_Renderer` for a window and clearing, drawing and presenting through it, tracked by handle the same way; `graphics/texture.cpp`: `IMG_LoadTexture` and the texture's size, tracked by handle the same way, and the one place a texture handle is minted, so a texture rasterized from a font enters the same registry as one loaded from a file; `graphics/font.cpp`: `TTF_OpenFont`, measuring a string and rasterizing one into a texture; `audio/sound.cpp`: `Mix_LoadWAV` and playing a chunk on any free channel; `audio/music.cpp`: `Mix_LoadMUS` and the transport of SDL_mixer's single music stream; `platform/input.cpp`: querying `SDL_GetKeyboardState`; `platform/gamepad.cpp`: opening and closing an `SDL_GameController` and querying its buttons and axes; `platform/filesystem.cpp`: `SDL_GetBasePath` and the asset root derived from it, plus `SDL_GetPrefPath` for the writable user data root; `platform/mouse.cpp`: querying `SDL_GetMouseState` and accumulating wheel deltas reported by `platform/events.cpp`). Each is bound to Haxe through a small `extern class` in the matching `fried.*` class. Game code never sees SDL2 directly, only `fried.Application`/`fried.Window`/`fried.Events`/`fried.input.Input`/`fried.graphics.Renderer`/`fried.graphics.Texture`/`fried.graphics.Font`/`fried.audio.Sound`/`fried.audio.Music`.

## Runtime (implemented so far)

`src/fried/` holds the engine's own Haxe code, split by domain into `fried` itself (what drives a program, and the window it drives), `fried.input`, `fried.io`, `fried.graphics` and `fried.audio`:

- `fried.Log`: `info`/`warn`/`error`, printing to stdout/stderr.
- `fried.Time`: `start()`/`tick()`, exposing `deltaSeconds`, `elapsedSeconds`, `frameCount`.
- `fried.Project`: the game's own identity and packaging data, declared in its `project.fried` and read at compile time, as `name()`, `organization()`, `version()` and `windowTitle()`. Described in its own section below.
- `fried.Window`: creates/destroys an SDL window (resizable), exposes `width`/`height`, and exposes the window's events as assignable callbacks: `onClose`, `onResize(width, height)` and `onFocusChanged(focused)`, all null until the game sets them. Resizes are reported from SDL's `SDL_WINDOWEVENT_SIZE_CHANGED` rather than `SDL_WINDOWEVENT_RESIZED`, since SDL only sends the latter for size changes the user or window manager caused. Reacting to a resize is optional: `width`/`height` always query SDL for the live size, so code that simply reads them every frame stays correct without touching the callbacks at all. A pure platform primitive: it has no renderer field and no renderer accessor, and nothing in it knows that renderers exist. A `fried.graphics.Renderer` is built *from* a window and is owned by `fried.Application`, never by the window, so the two can be reasoned about, created and destroyed separately.
- `fried.Application`: owns the SDL lifecycle (`init`/`shutdown`), the renderer, and the game loop itself: `run(update)` loops while `running` is true, pumping events (via `fried.Events`), ticking `fried.Time`, clearing the renderer, running `update`, presenting the renderer and ending the frame for `fried.input.Input` (in that order) each iteration; `quit()` stops it. The renderer is created here, not by the window: `createRenderer(window, vsync = true)` builds one, stores it as `Application.renderer` and returns it, `destroyRenderer()` drops it, and `shutdown()` drops it too if the game has not. Only one exists at a time, and a second `createRenderer()` throws rather than leaking the first. The loop clears before `update` and presents after it, so drawing code is only ever the middle of a frame that is already framed for it, and a game that draws nothing still commits a buffer every frame (which is what lets a Wayland compositor resize the window at all). A renderer is optional: with none, the loop runs exactly as it did before, minus the clear and the present.

  `targetFps` (60 by default, 0 to uncap) makes the loop sleep out whatever is left of the frame's budget, for the case where nothing else in the loop blocks: uncapped and without vsync, the loop spins a core at 100%. `Sys.sleep` only guarantees a minimum, so that sleep settles slightly under the target (measured: 59.2fps at 60). A vsync renderer already blocks in `SDL_RenderPresent` for exactly as long as the display needs, so while one is active `targetFps` is ignored entirely and the loop runs at the display's refresh rate (measured: 60.0fps through SDL's x11 driver on this machine). Sleeping on top of vsync is what that avoids: the sleep would push the next frame past the following vblank and halve the rate. A game that wants a cap below the refresh rate asks for a renderer with `vsync = false` and sets `targetFps`.
- `fried.Events`: `pump():Bool`, true if the application should quit (currently: an `SDL_QUIT` event was seen). It also drains the window events `native/platform/events.cpp` queued and dispatches each one to the callbacks of the `fried.Window` it belongs to, found through a registry `fried.Window` keeps by handle. Draining happens after the native pump has emptied SDL's queue, so a callback never runs while SDL state is still mid-update. Closing the last window needs no callback to work: SDL raises `SDL_QUIT` for it, which already ends the loop.
- `fried.input.Input`: keyboard, mouse and gamepad, all following the same three-state naming (deliberately matching Unity's `GetKey`/`GetKeyDown`/`GetKeyUp`, not the more common `IsKeyDown`-means-held convention): `isKeyPressed`/`isButtonPressed` (true every frame the key/button is held, from the frame it went down through the frame before it comes back up), `isKeyDown`/`isButtonDown` (true only on the single frame it went down), `isKeyReleased`/`isButtonReleased` (true only on the single frame it came back up). All three compare SDL's live state (kept current as a side effect of `fried.Events.pump()`'s `SDL_PollEvent` calls) against a previous-frame snapshot `fried.Application.run()` refreshes once per frame. `fried.input.Key` is an enum abstract over SDL's stable `SDL_SCANCODE_*` values (letters, digits, F1-F12, arrows, common control/modifier keys) and `fried.input.MouseButton` likewise over SDL's button ids (`Left`/`Middle`/`Right`), keeping SDL2 constants out of game code. Mouse also exposes `mouseX`/`mouseY` (position) and `scrollX`/`scrollY` (wheel delta accumulated this frame, reset every frame). The gamepad follows the same three states under its own names (`isGamepadButtonPressed`/`isGamepadButtonDown`/`isGamepadButtonReleased`) plus `getGamepadAxis(axis)`, `gamepadConnected` and `gamepadDeadzone`, and its previous-frame snapshot is refreshed by the same `endFrame()`.

`fried.input.GamepadButton` and `fried.input.GamepadAxis` are enum abstracts over SDL's `SDL_CONTROLLER_BUTTON_*`/`SDL_CONTROLLER_AXIS_*` values, the same way `Key` is over scancodes, but with names that describe a position rather than a label: the face buttons are `South`/`East`/`West`/`North`, so the same game code means the bottom face button on an Xbox pad (A), a PlayStation pad (cross) and the Vita (cross), and reads correctly on a platform whose labels are arranged differently. The rest are `Start`, `Select`, `Home`, `L1`/`R1`, `L2`/`R2`, `LeftStick`/`RightStick` (the stick presses) and `DpadUp`/`DpadDown`/`DpadLeft`/`DpadRight`. Axes are `LeftX`/`LeftY`/`RightX`/`RightY` plus `L2`/`R2`, normalized to `-1`..`1` (`0`..`1` for the triggers), with the sticks pointing the way the screen does, `-1` at left and up. Values below `gamepadDeadzone` (0.25 by default) read as exactly `0`, per axis rather than radially.

The two triggers are in both enums, because SDL reports them only as axes and a game wants them either way: `GamepadAxis.L2` is how far it is pulled, `GamepadButton.L2` is whether it is pulled past halfway, and the button form goes through the same three states and the same previous-frame snapshot as a real button. The two ids `GamepadButton` adds for them continue past SDL's own last button value, so every other id stays SDL's and needs no translation, and `native/platform/gamepad.cpp` is where those two turn back into an axis read. They are still written next to `L1` and `R1` in the enum, since where a member is declared is what a reader goes by and the numbers are only the bridge's business. The deadzone does not apply to the button form, so raising it does not move the point at which a trigger counts as pressed.

One gamepad is read at a time, the first one connected: `native/platform/gamepad.cpp` holds a single `SDL_GameController`, opened at `fried.Application.init()` if one is already plugged in and on `SDL_CONTROLLERDEVICEADDED` otherwise, closed on the `SDL_CONTROLLERDEVICEREMOVED` that names it, which then falls back to any other pad still connected. Nothing in the API is per-player yet, so nothing carries a player index yet.
- `fried.io.Filesystem`: where files are and how to read them, which is one question and so one class. Where: `basePath` (SDL's `SDL_GetBasePath()`, the directory the executable lives in) and the asset root, as `assetPath` plus `getAssetPath(relativePath)` which prefixes a path with it. `native/platform/filesystem.cpp` is the single place that decides where a platform keeps its assets (`<basePath>assets/`, and `app0:/assets/` on the Vita); platforms with a fixed mount point, such as Vita's `app0:/` or Switch's `romfs:/`, change that one function and nothing above it. Engine and game code never branch on platform to open an asset, and never build a path out of `basePath` by hand, and in practice they do not touch `assetPath` either: they go through `fried.io.Assets` below, whose macros are the only callers of `getAssetPath()`. How to read: `exists(path)`/`readBytes(path)`, a thin wrapper over hxcpp's own `sys.FileSystem`/`sys.io.File` rather than native glue, since (unlike windowing/input) the `cpp` target already implements these natively and cross-platform-enough for the PC scope currently verified. The wrapper exists so the implementation can be swapped for native/SDL glue later without touching call sites, if a target platform's `sys` support proves inadequate (e.g. Vita/Switch). Reading is scoped to generic, non-media data (config, level data); image/audio/font resources do not go through it. SDL's own libraries for those (SDL_image, SDL_mixer, SDL_ttf) load directly from a path and decode the format themselves, so each media resource is its own wrapper over the matching SDL library, independent of `Filesystem`: `fried.graphics.Texture`, `fried.graphics.Font`, `fried.audio.Sound` and `fried.audio.Music` each are. The two halves have different implementations (native glue for the roots, `sys.*` for the reads) but that is behind the API, and it is exactly the swap the wrapper was written to allow.
- `fried.io.Assets`: resolves a path in one of the two asset roots, `engine(relativePath)` for `<assetPath>engine/` and `game(relativePath)` for `<assetPath>game/`. Both are macros, which is how the engine/game split and the existence of every asset are checked at compile time (below). It resolves paths and nothing else: reading is `fried.io.Filesystem` for generic data, and `fried.graphics.Texture`, `fried.graphics.Font`, `fried.audio.Sound` or `fried.audio.Music` for media, each of which takes a path and is handed one of these.
- `fried.io.UserData`: the one writable location, where saves and user config go, as `path`, `getPath(relativePath)`, `exists()`, `read()` and `write()`. Described in its own section below, with the project file whose identity it is built from.
- `fried.graphics.Renderer`: what draws. Built from a `fried.Window` through `fried.Application.createRenderer()`, it wraps one `SDL_Renderer` (accelerated, alpha blending on) and exposes `clear()`, `present()`, `setDrawColor(r, g, b, a = 255)`, `drawTexture(texture, x, y, ?width, ?height)` (the size defaults to the texture's own) and the live `width`/`height` of its drawable area, which is the renderer's output size rather than the window's size, since the two differ on a scaled display. `clear()` fills the frame with the current draw color, following SDL's own semantics, so the clear color is just the last color that was set. `clear()` and `present()` are public but a game normally lets `Application.run()` call them around `update`. The constructor is not public: a renderer can only come from `Application.createRenderer()`, so the single owner cannot be bypassed by accident. `vsync` is read back from SDL after creation rather than remembered from what was asked for: a driver may not give vsync, and a loop that skips its fps cap because it believes it has vsync would then run unbounded. The engine asks for vsync by default and falls back to a renderer without it if that fails, so creation fails only when no accelerated renderer exists at all.
- `fried.graphics.Texture`: an image in renderer memory, with `width`/`height` read back from SDL rather than taken from the caller. It has two sources and therefore no public constructor: `Texture.load(renderer, path)` decodes and uploads a file in one `IMG_LoadTexture` step, and `fried.graphics.Font.renderText()` rasterizes a string into one. Both hand back the same type, so drawing code never learns which a texture came from. The path is whatever `fried.io.Assets` resolved, which is the only way a path is meant to be produced: `Texture` never takes a bare relative path and never goes through `fried.io.Filesystem`, so an asset that is missing is a compile error at the `Assets.game()` call rather than a null texture at load. It belongs to the renderer that created it (an `SDL_Texture` cannot outlive its `SDL_Renderer`), so `destroy()` it before the renderer goes.
- `fried.graphics.Font`: a typeface opened at one size, since that is what `TTF_OpenFont` gives, so a game that draws two sizes opens two fonts. `renderText(renderer, text, r, g, b, a = 255)` returns a `Texture`: SDL_ttf rasterizes the string (blended, so the edges are antialiased) and it is uploaded once, rather than the string being re-rasterized every frame. Text that changes is therefore a texture the game rebuilds when it changes and `destroy()`s like any other, which is the cost the API makes visible instead of hiding. `measureWidth(text)` and `lineHeight` answer where the next thing goes without rendering anything first.
- `fried.audio.Sound`: a short effect, decoded into memory by `Mix_LoadWAV` and played on whichever channel SDL_mixer has free, so the same sound can overlap with itself. `play(loops = 0)`, `stop()` (every channel currently playing this sound), `playing`, and `volume` as a 0..1 `Float` that is read back from SDL rather than remembered, since SDL_mixer's scale is 0..128 and the value therefore quantizes.
- `fried.audio.Music`: the streamed one, decoded as it plays. SDL_mixer has exactly one music stream, and that is the shape of the API rather than something hidden behind it: `play(loops = -1)` takes the stream over, and `pause()`, `resume()` and `stop()` on a `Music` that does not hold it do nothing, as do `playing`/`paused`, which are false for it. The native side tracks which handle holds the stream so this is decided per music rather than globally. `volume` is static, because SDL_mixer's music volume genuinely is one global value and an instance property would suggest otherwise.

All exercised together from `sandbox/src/Main.hx`, which adds `src/` to its Haxe classpath alongside its own `sandbox/src/`, standing in for a real game project. It keeps a small PNG and two WAVs in `sandbox/assets/` and the engine keeps a TTF in `assets/`, all generated for this repository so nothing third-party is vendored (the font is a placeholder that draws every printable ASCII character as the same filled box, enough to prove `TTF_OpenFont` gets a real file), copied next to the executable by CMake on every build (the asset root is resolved from `SDL_GetBasePath()`, so the assets have to sit beside the binary, not beside the sources); the sandbox resolves one asset from each root through `fried.io.Assets` and checks at startup that it really is there, so a build that populated only one of them fails loudly even though the macro already proved both exist in the sources. It then creates a renderer for its window, loads that PNG as a `fried.graphics.Texture` and draws it, scaled, in the middle of the window every frame, recentering itself as the window is resized, with a line of text rendered once through the engine's font drawn above it, its own music looping, and a sound on the space bar. It also counts its own runs, reading, incrementing and rewriting `saves/runs.txt` under its writable user data path at startup, and that count is both logged and drawn as the start of the line of text, since the Vita has no stdout to read it from.

## Asset roots (implemented)

Assets sit under the asset root `fried.io.Filesystem` resolves, split in two: `engine/`, shipped by the engine, and `game/`, shipped by the game. Engine code may read only the engine root; game code may read both.

The split exists only in the runtime layout. Each side keeps its own assets in a plain `assets/` directory in its own repository, and CMake copies the engine's `assets/` to `assets/engine/` and the game's `assets/` to `assets/game/` next to the executable. The copy is its own `ALL` target that depends on the executable, not a `POST_BUILD` command on it, since `POST_BUILD` only fires when the target relinks and an added or edited asset would then never reach the build tree. A game therefore never names the word `game` anywhere in its own tree: it has an `assets/` folder like the engine does, and the two only meet at runtime.

Nothing under the asset root is writable. That is not a rule the engine chose but the shape of the target platforms: Vita mounts the application read-only at `app0:` and Switch mounts `romfs:` read-only, so an asset API with a write side could not be implemented there anyway. State that has to survive a run (saves, user config) lives on a separate writable path, obtained from `SDL_GetPrefPath`, in its own class, `fried.io.UserData`, and is deliberately not part of the asset API.

`fried.io.Assets.engine()` and `fried.io.Assets.game()` are macros. Each call is replaced, at compile time, by a single `fried.io.Filesystem.getAssetPath("<root>/<path>")` with the whole subpath already folded into one constant, so the mechanism costs nothing at runtime. What the macro does before folding is the point:

- It resolves the path against the source tree of the root it belongs to and fails the build if the file is not there, so a typo in an asset name is a compile error at the call site rather than a load that returns null on a platform nobody tested. The engine's own `assets/` is found relative to `src/fried/io/Assets.hx` on the classpath, so a game inherits it without configuring anything; the game's own is `assets/` relative to the directory `haxe` runs in, overridable with `-D fried-game-assets=<dir>`.
- It reads `Context.getLocalClass()` and refuses `game()` to any caller whose package starts with `fried`. This is what imposes the engine/game asymmetry: engine code has only `engine()` available to it, game code has both, and there is no second class, second classpath or runtime path inspection anywhere. The check is on who is compiling the call, which is exactly the thing being restricted.
- It rejects an absolute path, or one containing `..`, so neither root can be used to walk into the other.

Which of the two roots a call means is a value, not a prefix string: a private `AssetRoot` enum abstract in `Assets.hx`, in macro context only, following the same pattern as `fried.input.Key` and `fried.input.MouseButton`. The names `engine` and `game` are written once each, there, and everything else (the runtime prefix and which source directory to verify against) is derived from the value, so the two cannot drift apart.

Both take their path as a macro constant rather than a `String` expression, so a path assembled at runtime does not compile. That is deliberate: constant paths are what make the two checks above possible on every asset reference in the program. It is a restriction that can be relaxed later (by falling back to an unverified runtime resolution for non-constant expressions) without invalidating a single existing call, whereas the reverse would not be true.

The boundary is a guard rail, not a sandbox: `fried.io.Filesystem.getAssetPath()` is public, and has to be, since the macro expands at the call site and that call site is game code, so engine code that wanted to could still build a `game/` path by hand. What the macro buys is that it cannot happen by accident, and that it is visible in review as a deliberate bypass.

## Project file and user data (implemented)

A game declares itself in a `project.fried` at its own root, next to the `build.hxml` that compiles it. It is JSON, because the file is written and rewritten by programs as much as by people: `haxe.Json` parses it in macro context, CMake reads it with `string(JSON ... GET ...)` (3.19 and up, and this repository already requires 3.20), and whatever emits one emits it with its own language's serializer instead of a format written for the occasion. The sandbox's is `sandbox/project.fried`:

```json
{
	"name": "Fried Sandbox",
	"organization": "Fried Engine",
	"version": "01.00",
	"window": {
		"title": "Fried Engine sandbox"
	},
	"vita": {
		"titleId": "FRIE00001"
	}
}
```

Every field in it is read by something today. `name` and `organization` are the game's identity, handed verbatim to `SDL_GetPrefPath()` to resolve the writable path below, so both have to be usable as directory names on every target; the engine does not sanitize them, since a silent rewrite would move a game's save directory without its author knowing. `version` and `vita.titleId` are what `sandbox/CMakeLists.txt` passes to `vita_create_vpk()`, which is also why the version is written in the `XX.XX` shape a Vita package requires. `window.title` is the title the game gives `fried.Window`. Each side reads only the keys it consumes: `vita.titleId` never reaches Haxe, `window.title` never reaches CMake.

`fried.Project` is how the identity reaches the engine: four macros (`name()`, `organization()`, `version()`, `windowTitle()`), each folded at compile time into the constant the file declares. Nothing passes an organization or an application name to `fried.Application.init()`, and nothing parses anything at runtime, so the file is an input to the build rather than something the game ships and opens. It is located the way the game's asset root is, `project.fried` relative to the directory `haxe` runs in, overridable with `-D fried-project=<path>`, so it never depends on where the engine itself sits. A missing or malformed file is a single `Context.fatalError`, since it is one fact about the whole project rather than a problem with a call site; a missing or non-string field is a `Context.error` per call site, so one compile reports all of them; an unknown key is ignored, so a file declaring more than this version of the engine consumes still builds. On the CMake side only the Vita branch reads it, because only packaging consumes those two fields, and the file is registered in `CMAKE_CONFIGURE_DEPENDS`, so editing it re-configures the build tree instead of quietly producing a package with stale values.

`fried.io.UserData` is that writable path: `path` (the root, with its trailing slash), `getPath(relativePath)`, `exists()`, `read()` and `write()`. Where the root lands is SDL's decision from the identity above, which is why this needed no branch of our own in `native/platform/filesystem.cpp`, unlike the asset root: `$XDG_DATA_HOME/<organization>/<name>/` on Linux, `%APPDATA%\<organization>\<name>\` on Windows, `ux0:/data/<organization>/<name>/` on the Vita, created by SDL if it is not already there. Every path goes through `getPath()`, which rejects an empty, absolute or `..`-containing relative path the way the asset macros reject one at compile time, and `write()` creates the directories its relative path names, since SDL only creates the root itself. It is initialized by `fried.Application.init()` right after `fried.io.Filesystem`, and it throws instead of falling back to some other directory if SDL cannot resolve one, because a game silently saving somewhere nobody asked for is worse than one that does not start.

`fried.io.Filesystem` gained nothing in the process: it still cannot write. The only writes the engine can perform are relative to the user data root, which is what keeps "nothing under the asset root is writable" a property of the API rather than a convention that holds until somebody builds a path by hand.

## PlayStation Vita (implemented)

A Vita build is a second CMake build tree configured with the toolchain file VitaSDK ships (`cmake -S . -B build/vita -DCMAKE_TOOLCHAIN_FILE=$VITASDK/share/vita.toolchain.cmake`). That toolchain sets `VITA`, and every Vita branch in this repository keys off it, so there is no platform flag of our own and no second entry point: the same `CMakeLists.txt` files build both platforms. The Haxe side is untouched, since the C++ hxcpp generates is the same on every target.

`cmake/Vita.cmake` is the packaging step, and only that: `fried_add_vita_vpk()` wraps VitaSDK's own `vita_create_self()`/`vita_create_vpk()` to produce the `.vpk` the console installs, with the LiveArea files the game keeps in its own `sce_sys/` and both asset roots packed under `assets/`, so `app0:/assets/engine/` and `app0:/assets/game/` are the same layout the PC build copies next to the executable.

The LiveArea files in `sandbox/sce_sys/` are palette PNGs (color type 3), not truecolor: the console's installer rejects a truecolor `icon0.png` or LiveArea image at the end of the install, with the package otherwise valid.

What the port actually cost is in `cmake/Hxcpp.cmake`: hxcpp has no Vita target of its own, and its runtime is written against glibc. `HX_LINUX` and `NEKO_LINUX` select its generic POSIX paths, `HXCPP_NO_DYNAMIC_LOADING` compiles out the `dlopen()` layer for a console that loads no shared libraries, and `cmake/vita/newlib/` fills the three gaps that leaves: headers newlib does not ship (`xlocale.h`, `sys/termios.h`), POSIX that its own headers hide from hxcpp (`PATH_MAX`, the wait status macros), and `readlink()`, which newlib declares and VitaSDK does not implement. `sys.io.Process` and `sys.net.Socket` are left out of the build: the Vita has no subprocesses, and its sockets are a Sony API rather than the BSD one hxcpp calls. Haxe code that uses either fails to link rather than failing on the console.

The engine's own C++ needed one branch, in `native/platform/filesystem.cpp`, for the fixed read-only mount point. The writable path needed none: VitaSDK's SDL2 implements `SDL_GetPrefPath()` and answers `ux0:/data/<organization>/<name>/`, creating it if it is not there, and hxcpp's `sys.io.File` writes to it through newlib, verified on hardware. Everything else in `native/` compiles unchanged, because VitaSDK ships SDL2 and its three companion libraries: the window, the event loop, the renderer, the textures, the fonts and the audio are the same SDL2 calls on both platforms. They are linked as static libraries under their own target names there, with the dependencies VitaSDK's freetype and SDL2 packages leave unnamed (`png`, `z`, `bz2`, `pthread`) declared in `sandbox/CMakeLists.txt`.

The Vita has no keyboard or mouse, so `fried.input.Input` reports nothing through those two there; its buttons and sticks arrive as the gamepad, which VitaSDK's SDL2 exposes as an ordinary `SDL_GameController` with no branch of its own. Not addressed yet: touch input.

## Source layout

Both source trees are split by domain, but not by the same domains, because the two sides are read by different people asking different questions.

`native/` is split by where an implementation comes from: `platform/` is the platform layer in the usual sense, the things the operating system and the hardware provide rather than the game (the SDL lifecycle, the window, the OS event queue, the keyboard, the mouse, the gamepad, where the executable lives), `graphics/` is what draws, and `audio/` is what plays. Whoever opens `native/` is asking which SDL calls the engine makes and what a new platform would have to answer for, so the layer is exactly the right grouping there.

`src/fried/` is split by concept, because whoever opens it is writing a game and thinks in `Renderer`, `Key` and `Assets`, not in layers: `fried` itself holds what drives a program and the window it drives (`Application`, `Window`, `Events`, `Project`, plus `Log` and `Time`, which everything reports through), `fried.input` the keyboard, mouse and gamepad, `fried.io` where files are, how to read them and where a game may write, `fried.graphics` what draws, `fried.audio` what plays. `Window` sits at the root next to `Application` rather than in a domain of its own, since a game treats it as fundamental, and `Events` sits with it because it is the machinery that delivers a window's callbacks.

So `fried.input.Key` is glued by `native/platform/input.cpp`, and that is deliberate rather than an oversight: a keyboard is part of the platform layer and part of input, and each tree names it the way its own reader would look for it.

There is no platform axis in either tree, and above the glue there cannot be one: the whole point of `native/` is that the Haxe side never learns which platform it is on. Below it, a header is the contract, shared by every platform, because it is what the `@:include` of the extern names. `native/` is a single include root, so those names are paths within it (`@:include("graphics/renderer.h")`) and the domain folders cost the Haxe side nothing.
